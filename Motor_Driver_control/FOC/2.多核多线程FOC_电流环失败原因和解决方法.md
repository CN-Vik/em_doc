这是一个非常经典的双核/RTOS架构下做FOC常踩的坑。你的直觉非常敏锐，**“电角度和电流值肯定不同步，差几百us” 以及 “1kHz的电角度采样” 就是导致这个恶性死循环的绝对元凶。**

你给出的前馈解耦和PI计算代码本身**没有任何问题**，非常标准。问题出在了系统的**时序和架构**上。

我们来抽丝剥茧，逐一分析为什么会出现“堵转正常、一转就疯”，以及为什么简陋的Arduino反而能跑通。

### 1. 核心元凶：1kHz 的电角度采样 vs 20kHz 的电流环

FOC的核心是**磁场定向**，也就是用Park变换和反Park变换，把定子上的交流电转化为转子坐标系下的直流电（$i_d$, $i_q$）。这个变换**强依赖于实时的电角度 $\theta_{elec}$**。

* **当你堵转时：** 电机不转，$\theta_{elec}$ 是个常数。无论你采样多慢，你的坐标系是稳固的。此时电流环等效于控制一个固定的RL电路，所以PI参数能完美发挥作用，电流能控住。
* **当电机转起来时：** $\theta_{elec}$ 开始快速变化。你的FOC运算是 20kHz（50us一次），但你的电角度是 1kHz（1000us更新一次）。这意味着**在连续的20个PWM周期里，你的FOC算法用的是同一个“过期”的电角度**。

**恶性死循环的产生过程：**

1. 电机转动，真实的转子角度已经跑了，但你的算法还在用1ms前的旧角度进行 Park 变换。
2. 坐标系偏离导致**投影错误**：你以为你在测 $i_q$（产生扭矩），但因为角度错了，你测到的其实是 $i_q$ 和部分 $i_d$ 的混合体，甚至可能符号都反了。
3. 你的PI控制器发现“哦？$i_q$ 没达到设定值”，于是拼命增加 $v_q$ 输出。
4. 反Park变换再次使用了这个“错误的旧角度”，把巨大的 $v_q$ 施加到了定子上。但由于角度错位，这个电压并没有加在q轴上，而是产生了一个畸变的磁场，导致电机非预期加速。
5. 电机转速越来越快，1ms内的角度误差变得极其巨大，系统彻底发散，进入你说的“狂飙死循环”。

### 2. 几百微秒的延迟意味着什么？

在高速运转时，几百微秒的延迟是致命的。
假设电机电频率是 200Hz（比如7对极电机，转速约 1700 RPM）：

* 1个电周期是 $1 / 200 = 5ms$（5000us）。
* 你的采样差了 500us，相当于电角度差了 $500 / 5000 \times 360^\circ = 36^\circ$！
* 坐标系偏了 $36^\circ$，$cos(36^\circ) \approx 0.8$，你不仅损失了 20% 的有效力矩，还把大量的 $v_q$ 串到了 d 轴上，引发严重的交叉耦合和效率暴跌，甚至反转。

### 3. 为什么 DengFOC (Arduino) 能做成？

因为简单的单片机程序往往是**强顺序执行 (Strictly Sequential)** 的单线程：

```c

    foc_math(theta, i_a, i_b); // 3. 计算FOC

```

尽管Arduino的主频很低，整个Loop可能只能跑 2kHz 或 5kHz，**但它的角度 $\theta$ 和电流 $i$ 在时间上是绝对对齐的**。它算得慢，但算得“准”，坐标系没有发生严重的滑移，因此 PI 能够正常收敛。

你的 ESP32 性能虽然强，但由于把任务拆分到了不同的 CPU 核心，且更新频率不一致（20kHz vs 1kHz），导致了严重的数据撕裂（Data Tearing）和相位延迟。

### 🛠️ 解决办法：重构 ESP32 的 FOC 时序

要解决这个问题，必须遵循 FOC 的铁律：**“同生共死，同频同相”**。位置读取、电流采样和 FOC 运算必须在同一个高频中断/任务中顺序完成。

#### 建议的架构调整：

**在核心 0 (或者高优先级中断) 中运行 20kHz 的电流环：**
这必须是一个严格串行的过程，绝对不能让角度变成“滞后变量”。

1. **PWM 触发 ADC 采样中断** (20kHz)。
2. **在中断里第一件事：** 立即读取/更新电角度（如果你的编码器是通过SPI/I2C读取，尽量用硬件SPI并拉高波特率，确保在几微秒内读完）。
3. **读取 ADC 电流值**。
4. **执行你提供的 FOC 代码** (Park, PI, 解耦, InvPark)。
5. **更新 PWM 占空比**。

**在核心 1 中运行低频任务 (1kHz)：**

1. **速度环 / 位置环计算**：根据 20kHz 任务共享出来的角度计算速度，运行速度环 PI，计算出目标的 `i_q_ref`，通过队列或全局变量（加 Volatile 和内存屏障）传给高频任务。
2. **串口通信 / 逻辑调度**。

#### 临时补救方案（角度补偿）：

如果你因为硬件限制（比如编码器通信太慢），实在无法在 20kHz 任务里读取角度，你必须加入**基于速度的延时补偿**：

```c
// 假设你有一个从另一个核心传过来的 1kHz 更新的角度 theta_1khz 
// 以及算出来的电角速度 omega_elec
// 和一个测量/通信带来的时间差 t_delay (秒，比如 0.0005s)

// 在 20kHz 的 FOC 任务中，用前馈预测当前真实角度：
float current_time_offset = get_time_since_last_1khz_update(); 
theta_current = theta_1khz + omega_elec * (current_time_offset + t_delay);

// 然后再用这个 theta_current 去做 Park 变换和合成计算

```

*注：这只是补救，强烈建议采用上面提到的强顺序读取架构。*

**总结：** 你的控制算法写得没问题，是“多核异步”摧毁了电角度的实时性。把读取角度的代码搬到 20kHz 的 FOC 计算之前，确保每次计算时电流和角度的时间戳是吻合的，你的电机马上就能乖乖转起来。

**灾难现场还原：**
假设电机在转动，你的 20kHz 任务在 1 毫秒内会执行 20 次 FOC 运算。

### 3. 你现在该咋办？

既然知道了病因是“角度和电流不同步”，你要解决它，就必须让核心的数据采集和计算在**同一个高频时间线上**完成。这里给你三个方案：

#### 方案 A：回归纯粹的串行（最稳妥，先跑通再说）

3. 读电流。
4. 算 FOC。
5. 更新 PWM。
*注意：这个方案的频率上限取决于你的编码器读取速度。*

#### 方案 B：硬件升级（真正的 20kHz FOC）

如果你非要保持 20kHz 的电流环控制（高性能伺服必须如此），那么你的角度读取速度就必须跟上！
如果你的编码器像 DengFOC 一样是 I2C 的 AS5600 ，那是绝对不可能在 20kHz 中断里读完的（I2C 通信耗时远超 50us，会直接卡死 CPU）。

* **做法：** 换编码器（比如 MT6816、AS5047P），走 **高速 SPI** 或者 **ABZ 正交解码**（ESP32 有硬件 PCNT 外设可以硬件解析 ABZ，不占 CPU 时间，随时读取都是最新角度）。然后在你的 20kHz ADC 中断里，瞬间读出硬件角度，再做计算。

#### 方案 C：软件观测器补偿（不改硬件的无奈之举）

如果只能 1kHz 读角度，又想 20kHz 跑控制，你必须在 20kHz 的任务里写一个**角度插值预测（PLL/观测器）**。
利用 1kHz 任务算出来的机械角速度 $\omega$，在 20kHz 的任务里实时推算当前的真实角度：
$\theta_{now} = \theta_{last\_1kHz\_read} + \omega \times \Delta t$
然后用这个推算出来的 $\theta_{now}$ 去做 Park 变换。

### 第一步：废除双核隔离，回归单线程 (The DengFOC Way)

把所有的核心运算全部拉到一个任务（或定时器中断）里。**必须严格保证在同一次循环内：先拿最新角度 $\rightarrow$ 再拿最新电流 $\rightarrow$ 立刻算 FOC $\rightarrow$ 立刻出 PWM。**

把你原来的架构改成下面这种纯顺序结构：

```c
// 建议放在一个 1kHz 或 2kHz 的定时器中断/高优先级 RTOS Task 中
void FOC_Current_Loop_Task() {
    
    // 1. 【绝对同步】获取当前电角度 (阻塞读取)
    // 这一步虽然慢(I2C耗时)，但必须等它读完！
    float theta_elec = get_electrical_angle(); 

    // 2. 获取当前相电流
    float i_a = read_current_a();
    float i_b = read_current_b();
    
    // 3. Clark & Park 变换 (必须用刚刚读到的 theta_elec)
    float i_alpha = i_a;
    float i_beta = (i_a + 2.0f * i_b) / sqrt(3.0f);
    float i_d_fdb = i_alpha * cos(theta_elec) + i_beta * sin(theta_elec);
    float i_q_fdb = i_beta * cos(theta_elec) - i_alpha * sin(theta_elec);

    // 4. PI 控制计算
    v_d_pi = pi_run(&pi_d, i_d_ref - i_d_fdb);
    v_q_pi = pi_run(&pi_q, i_q_ref - i_q_fdb);

    // 5. 解耦补偿 (直接用你原来的代码)
    v_d_comp = -omega * L_q * i_q_fdb;
    v_q_comp = omega * L_d * i_d_fdb + omega * psi_m;

    // 6. 合成与限幅
    v_d = v_d_pi + v_d_comp;
    v_q = v_q_pi + v_q_comp;
    limit_voltage_d_axis_priority(&v_d, &v_q, v_max);

    // 7. InvPark 变换 & SVPWM 输出 (必须用同一个 theta_elec)
    float v_alpha = v_d * cos(theta_elec) - v_q * sin(theta_elec);
    float v_beta = v_d * sin(theta_elec) + v_q * cos(theta_elec);
    set_pwm(v_alpha, v_beta); 
}

```

### 第二步：大幅降低 FOC 运算频率

* **注意：** 你的 PWM 载波频率依然可以保持 20kHz 不变（硬件发波不受影响），但更新占空比（FOC 运算）的频率降下来，迁就你那颗 AS5600 慢吞吞的读取速度。

### 第三步：重新调整 PID 参数

因为你的控制频率从 20kHz 骤降到了 1kHz 左右，系统的采样周期（$T_s$）变大了 20 倍。

### 1. 核心矛盾：数据刷新率与控制频率极度脱节

* **你的硬件时序：** 你的控制闭环（FOC 坐标变换和 PID 计算）运行在 20kHz 的中断里（每 50 微秒执行一次），但你的眼睛（电角度采样）却运行在另一个核心的 1kHz 任务里（每 1000 微秒才更新一次）。
* **致命的“盲打”：** 在电角度更新一次的 1 毫秒空档期内，你的 FOC 计算已经被执行了 20 次。这意味着，在这连续的 20 个控制周期里，你的大脑一直在使用同一个**已经严重过期、静止不动的“历史电角度”**。

### 2. 物理灾难：Park变换坐标系严重滑移

* **FOC的命门：** FOC 的核心是将定子上的交流电流，精准投影到跟着转子一起旋转的 d-q 坐标系上。这极度依赖当前那一瞬间极其精准的转子位置（$\theta$）。
* **坐标系错乱：** 电机一旦转起来，物理转子在飞速往前跑，但你的数学运算还在用 1 毫秒前的位置做 Park 和反 Park 变换。这导致你自以为在测量并控制 q 轴（扭矩电流），但由于坐标系偏离，你测量到的其实是 $I_q$ 和 $I_d$ 的一团糊涂账。

### 3. 彻底崩溃：PI 控制器的“恶性正反馈循环”

这就是你观察到“误差越来越大、输出越来越猛、转速越来越快”的直接原因：

1. **产生误判：** PI 控制器因为使用了错误的角度，算出了一个畸变的 $I_q$ 反馈值。它发现这个假 $I_q$ 总是达不到目标，于是开始用力积分。
2. **疯狂输出：** PI 控制器为了弥补这个虚假的误差，拼命增大 $V_q$（电压输出）。
3. **南辕北辙：** 紧接着，这个巨大的 $V_q$ 在反 Park 变换时，再次被乘以了那个“过期的旧角度”。导致巨大的电压并没有加在预期的方向上，而是打偏了，产生了一个极其强烈的错误磁场，一脚油门把电机踹得飞转。
4. **万劫不复：** 电机转速一变快，1 毫秒内的角度滑移误差就变得**更加巨大** -> 坐标系偏离更离谱 -> PI 算出更疯狂的 $V_q$ -> 电机转得更疯。系统彻底进入了无法挽回的正反馈死循环。

### 4. 架构误区：“多核异步”不等于“高性能控制”

* **你踩的坑：** 利用 ESP32 的双核与 RTOS，把任务拆分来榨取 CPU 性能，这是做互联网 IoT 开发的好习惯，却是做底层伺服控制的噩梦。在没有使用“观测器/卡尔曼滤波”对慢速角度进行高频插值预测的情况下，直接在两个异步核心之间传递 FOC 核心变量，数据撕裂是必然的。
* **DengFOC 为什么能赢：** 简陋的 Arduino 代码虽然整体频率可能连 2kHz 都不到，但它的 **[读角度 -> 读电流 -> 算PID -> 输出PWM]** 是一个**强绑定的、原子的串行过程**。它算得慢，但它的坐标系永远是对齐的，所以系统能稳稳收敛。

# >>>为啥dengfoc 单循环顺序执行反倒可以呢？？

这个问题问得太有水平了！这说明你已经触碰到了电机控制里最核心的本质——**“控制频率”和“数据一致性”的区别。**

你现在的疑惑是：既然 FOC 对实时性要求这么高，DengFOC 的 `while` 循环那么慢（可能只有 1kHz 甚至几百 Hz），按理说延迟也很大，为啥它就能稳稳当当地控制住电流，而不像你的双核架构那样“发疯”？

核心原因就四个字：**“逻辑自洽”**。

我们把 FOC 剥开来看，下面这三点彻底解释了 DengFOC 为什么慢却能成功，以及它和你的双核架构在本质上的不同：

### 1. 内部坐标系的“绝对一致性”（没有被撕裂）

FOC 的数学模型（Park变换和反Park变换）是一个瞬时方程。它只要求一件事：**你送进公式的电流 $I$ 和角度 $\theta$，必须描述的是同一个物理瞬间。**

我们来看看 DengFOC 单个 `while` 循环里的微观时间轴：

1. **耗时 500us：** 等待 I2C 慢吞吞地读完 AS5600 的角度 $\theta$。
2. **耗时 10us：** 瞬间读完 ADC 的电流 $I_a, I_b$。
3. **耗时 5us：** 用刚才读到的 $\theta$ 和 $I$ 做 Park 变换，算出版的 $I_q$。
4. **耗时 5us：** PI 控制器算出 $V_q$。
5. **耗时 5us：** **用同一个 $\theta$** 将 $V_q$ 逆变换回定子坐标系，更新 PWM。

在这个过程中，虽然整个循环跑完花了大半个毫秒，非常慢。但是！**它的电流 $I$ 和角度 $\theta$ 在时间上只差了十几微秒**。
更重要的是，它用来计算当前状态的 $\theta$，和它用来输出电压的 $\theta$，是**同一个值**。它的数学逻辑是完美自洽的：它在“那一瞬间”准确测量了误差，并在“那一瞬间”的角度方向上施加了正确的电压。

### 2. 打个比方：狙击手 vs 闭眼机枪手

* **DengFOC（慢但同步）：** 就像一个动作很慢的狙击手。他花 1 秒钟瞄准（读角度+读电流），然后开一枪（计算+输出 PWM）。虽然他开枪频率很低，但他每次开枪时，眼睛看着的都是目标**此刻**的位置，所以他能打中，系统是稳定的。
* **你的双核架构（快但不同步）：** 就像一个疯狂的机枪手（20kHz 的电流环），但他每秒钟只睁开一次眼睛（1kHz 的角度读取）。他看了一眼目标，**然后闭上眼睛，在接下来的 1 毫秒内，朝着刚才那个残影疯狂开了 20 枪。** 但现实中目标（转子）已经跑偏了，这 20 枪全部打在了错误的方向（把 $V_q$ 打到了 d 轴上），导致了不可控的严重后果。

**DengFOC 的秘诀在于：它宁可不开枪（降低控制频率），也绝对不闭着眼睛瞎开枪。** 它每次 FOC 计算，用的都是全新鲜出炉的角度。

### 3. DengFOC 真的完美吗？它的致命弱点在哪里？

不要以为 DengFOC 这样搞就万事大吉了，它虽然能控制住，但这种“低频顺序执行”在**电机高速运转**时会原形毕露。

既然整个 loop 耗时这么长，会发生什么？

* **相位滞后（Phase Lag）：** 当电机转速很快时（比如几千转），在 DengFOC 读完角度、算完公式、到最后更新 PWM 的这几百微秒里，**真实的物理转子其实已经往前转了一个不可忽略的角度**。
* **后果：** 你的定子磁场总是“慢半拍”追不上转子。表现出来就是：电机低速很平滑，但**转速上不去**，一旦到了中高速，电流效率极速下降（本来应该 1A 能出的力，现在需要 2A），电机严重发热，最终失步停转。

### 总结：你的破局之道

你的双核架构初衷是好的（为了提高控制频率，解决高速时的相位滞后），但你犯了“数据不同步”的大忌。

1. **FOC 的底线是同步：** 无论频率多低，必须保证 $\theta$、电流采样、PWM 更新这三者在一个原子的、不可打断的执行流里完成。这就是为什么让你先降频、退回单线程去跑通电流环。
2. **FOC 的上限是频率：** 等你用单线程跑通了，想要电机跑得飞快、性能炸裂，你要解决的不是把 FOC 任务和角度任务拆到两个核，而是**想尽一切办法提升“获取角度的速度”**（比如换 SPI 编码器、换 ABZ 硬件解码）。只有当“读角度”和“读电流”都能在 50us 内搞定时，你才能真正驾驭 20kHz 的完美电流环。

# >>>dengfoc 有用PWM ISR吗

**完全没有！** 你翻遍你发给我的这几百行 DengFOC (V0.2) 的源码，**里面绝对找不到任何一个硬件定时器中断（Timer Interrupt）或者 PWM 中断服务函数（ISR）。**

这也是我之前强调它是一个“典型的单线程、顺序执行的裸机轮询架构”的根本原因。

我们可以从你提供的代码里找到三大“铁证”，来看看它是怎么运作的：

### 铁证 1：主循环全靠 `loop()` 死扛

看它的主函数结构：

```cpp
void loop() 
{
  runFOC(); // 里面包了读角度和读ADC
  DFOC_M0_SET_CURRENT_PID(5,200,0,100000);
  DFOC_M0_setTorque(serial_motor_target()); // 里面包了算FOC和写PWM
  // ... 其他代码
}

```

所有的操作都是在这个 Arduino 的默认 `loop()` 里面一遍又一遍地死循环（Polling）。没有任何硬件中断来打断或者定时触发它。它能跑多快，完全取决于这个 `loop()` 里面最慢的那行代码（通常是 I2C 读 AS5600 角度）执行需要多久。

### 铁证 2：软件阻塞式的 ADC 采样

你看它的电流采样是怎么写的：

```cpp
float CurrSense::readADCVoltageInline(const int pinA){
  uint32_t raw_adc = analogRead(pinA); // 核心在这里！
  return raw_adc * _ADC_CONV;
}

```

它用的是 Arduino 最基础的 `analogRead()` 函数。

* **真正的高性能 FOC（比如 STM32）：** 是 PWM 计数器到达顶点时，**硬件自动触发** ADC 开始采样，采完后进入中断。CPU 根本不需要等。
* **DengFOC 的做法：** 走到这一行代码时，CPU 会发命令给 ADC：“嘿，给我采个样”，然后 CPU 就**停在这里傻等（阻塞）**，直到 ADC 转换完成返回结果，程序才接着往下走。这也是为什么它不需要（也不能）用 PWM 中断的原因。

### 铁证 3：简单的占空比写入

看它的 PWM 输出代码：

```cpp
void setPwm(float Ua, float Ub, float Uc) {
  // ... 算占空比
  ledcWrite(0, dc_a*255);
  ledcWrite(1, dc_b*255);
  ledcWrite(2, dc_c*255);
}

```

`ledcWrite` 是 ESP32 官方提供的一个上层 API，用于生成软件控制的 PWM。它仅仅是改变了 PWM 控制器的寄存器值而已，并没有绑定任何底层的周期中断（像 STM32 的 Update Interrupt 或是硬件死区控制）。

---

### 总结：大道至简，但也受限于此

DengFOC 之所以能跑通电流环，靠的不是高深的中断控制，而是“粗暴但绝对同步的软件流水线”。

它强行把**获取电角度、获取电流、进行 PI 计算、输出 PWM** 这四个动作捆绑在一个 `loop()` 里顺序执行。虽然整体控制频率可能被 I2C 拖累到了 1kHz 甚至更低，但因为没有中断打乱节奏，它送入 FOC 公式的电流和角度在时间上永远是“新鲜且匹配”的，这就足够让 PI 控制器收敛了。

如果你要在 ESP32 上暂时模仿它跑通，就一定要学它这种“放弃并发，回归串行”的思路，把所有的运算放在一个按顺序执行的 Task 里！
