# 猫砂盆「手机在家、设备在公司」远程控制 完整通信原理+全流程拆解
先给核心结论：
**不靠手机直连设备，靠「中间云端服务器」中转**
底层：**全程 TCP**
应用层：**MQTT**
配网/账号/固件辅助：**HTTP/HTTPS**

## 一、先搞懂关键前提（为什么不能直连）
1. 猫砂盆、手机都在各自路由器**内网**，都是局域网私有IP；
2. 运营商和路由器**禁止外网主动访问内网设备**（NAT防火墙）；
3. 所以**手机永远无法直接发起TCP/UDP连到公司的猫砂盆**；
4. 解决方案：**设备主动长连接连云端**，永远在线，等指令。

---

# 二、整体架构三层
1. **终端层**：ESP32猫砂盆（MQTT客户端）
2. **服务层**：云端MQTT服务器（Broker，中间人转发）
3. **控制层**：手机APP（MQTT客户端）

三者地位平等，都是MQTT客户端，服务器只做转发，不处理业务逻辑。

---

# 三、完整通信全流程（分5步，从头到尾）
## 第一步：猫砂盆上电，自动连云
1. 猫砂盆连上公司WiFi；
2. **主动发起TCP连接**，连上公网MQTT服务器；
3. 完成MQTT登录、鉴权、上报设备ID；
4. **订阅专属下行指令主题** `device/xxx/cmd`；
5. 维持**TCP长连接+心跳包**，一直挂在云端，永不断开。

> 重点：是**设备主动连服务器**，不是服务器连设备，绕过路由器NAT限制。

## 第二步：手机APP登录绑定设备
1. 手机用4G/5G/家里WiFi，连公网；
2. APP通过**HTTPS**登录账号、拉取绑定的设备列表；
3. APP也连上同一个**MQTT云端**；
4. APP订阅设备**上行状态主题** `device/xxx/status`。

## 第三步：你手机点「一键清理」
1. APP构造控制指令：清理、模式设置等；
2. APP **发布(Publish)** 到主题 `device/xxx/cmd`；
3. 消息发到MQTT云端服务器。

## 第四步：云端转发给猫砂盆
1. 云端收到主题消息；
2. 查询谁订阅了这个主题 → 找到公司在线的猫砂盆；
3. 把指令**转发**给猫砂盆的TCP长连接通道。

## 第五步：设备执行+状态回传
1. 猫砂盆收到MQTT指令，解析后启动电机清理；
2. 执行后，主动**发布状态**到 `device/xxx/status`；
3. 云端转发给手机APP；
4. APP界面刷新：清理中/已完成/砂满告警。

---

# 四、底层协议拆解
1. **物理传输**：4G/5G/WiFi 公网IP路由
2. **传输层**：**纯TCP**（长连接、可靠不丢包）
3. **应用层**：**MQTT**（发布订阅、主题转发、心跳保活）
4. **辅助协议**：
   - 配网、登录、固件升级 → **HTTP/HTTPS**
   - 全程**不用UDP**、不用WebSocket、不用裸TCP直连

---

# 五、为什么不用你说的 裸TCP / UDP / WebSocket？
1. **裸TCP**：只能同局域网直连，跨网穿透不了路由器NAT，远程用不了；
2. **裸UDP**：不可靠，指令容易丢，无长连接保活，设备没法一直在线；
3. **WebSocket**：给浏览器/网页用的，没有物联网设备必备的遗嘱、QoS、离线消息，不适合硬件长连接。

---

# 六、一句话极简概括流程
猫砂盆**主动长连接挂云端** → 手机异地发指令到云端 → 云端**转发**给设备 → 设备执行+回传状态 → 手机刷新界面。

---

# 七、额外补充：心跳&掉线机制
- 猫砂盆每隔几十秒发**MQTT心跳**，告诉云端“我还在线”；
- 断网/断电后，云端检测连接断开，自动标记设备离线；
- 设备重新上电，自动重连云端，恢复远程控制。

# 猫砂盆 远程跨网控制 完整架构+通信流程（文字拓扑图+一步步走通）
## 一、整体拓扑架构
```
手机APP（在家/4G/5G）
       ↓ 公网互联网
【MQTT云端服务器Broker】 （中间人转发）
       ↓ 公网互联网
猫砂盆（在公司WiFi内网）
```
核心关键点：**设备主动连云，手机也连云，互相不直接连线**。

## 二、分层协议栈
- 物理层：WiFi / 4G / 5G 公网
- 传输层：**全程 TCP 长连接**
- 应用层：**MQTT**（主控控指令+状态上报）
- 辅助：登录/绑定/OTA 用 HTTPS

## 三、完整通信分步流程（按时间顺序）
### 1. 猫砂盆上电入网常驻
1. 猫砂盆连上公司 WiFi，拿到内网 IP
2. 主动向外发起 **TCP 连接** → 连上公网 MQTT 服务器
3. MQTT 鉴权登录（设备ID/密钥）
4. 订阅专属下行主题：`device/设备ID/cmd`  （等着收手机指令）
5. 定时发 MQTT 心跳，维持 TCP 长连接，**永久在线挂着**

> 原理：内网设备主动往外连，路由器NAT就会保留这条通路，外网服务器能下发数据进来。

### 2. 手机APP 连云绑定
1. 手机用家里宽带/4G/5G 上网
2. APP 先走 **HTTPS** 登录账号、拉取已绑定设备列表
3. APP 也连接同一个 MQTT 服务器
4. APP 订阅设备上行主题：`device/设备ID/status` （等着收设备状态）

### 3. 你手机点击「一键清理」
1. APP 封装控制指令 JSON/二进制：`action: start_clean`
2. APP 往主题 `device/设备ID/cmd` **Publish 发布消息**
3. 消息到达 MQTT 云端服务器

### 4. 云端中转下发
1. MQTT 服务器看：谁订阅了 `device/设备ID/cmd`？
2. 找到在线的**公司猫砂盆**
3. 把指令通过早已建立的 **TCP长连接** 转发给猫砂盆

### 5. 设备执行 + 状态回传
1. 猫砂盆收到 MQTT 指令，解析、启动电机清理
2. 设备主动发布状态：`state: cleaning` 到 `device/设备ID/status`
3. 云端转发给订阅中的手机APP
4. APP 刷新界面：显示清理中、剩余时间、完成状态

## 四、为什么手机在家、设备在公司也能控？
1. 两边都不用互相找对方 IP
2. 都只认**公网MQTT服务器**
3. 设备永久长连接在线，永远留着通道
4. 不管手机在哪，只要能上网，连云端就能发指令

## 五、直白总结一句话
**猫砂盆主动挂在云端不走，手机在哪都连云端发指令，云端帮忙转发，就实现跨城市远程控制。**

## 六、补充：和裸TCP/UDP的本质区别
- 裸TCP：只能同WiFi局域网直连，**跨网穿透不了路由器**
- 裸UDP：不可靠，指令易丢，没法做长连接常驻
- MQTT+云端TCP：天生解决**跨网、NAT穿透、长连接、可靠指令**，就是你现在猫砂盆的标准方案。

# 猫砂盆 MQTT 标准主题规范 + 通信JSON报文模板（可直接前后端、ESP32 落地开发）
## 一、统一主题命名规则
采用分级格式：`产品品类/设备唯一ID/功能类型`

### 固定主题定义
1. **设备下行指令主题（APP→设备）**
```
catlitter/{devId}/cmd
```
- 用途：APP 下发控制指令、参数设置
- 订阅方：**猫砂盆ESP32**
- 发布方：手机APP

2. **设备上行状态上报主题（设备→APP）**
```
catlitter/{devId}/status
```
- 用途：设备上报运行状态、传感器数据、故障告警
- 订阅方：**手机APP**
- 发布方：猫砂盆ESP32

3. **设备回执应答主题（指令响应）**
```
catlitter/{devId}/reply
```
- 用途：设备收到指令后，回复「已接收/执行成功/失败」
- 解决：APP 知道指令有没有生效

> devId 换成设备唯一编号，比如 `CL20260513001`

---

## 二、APP 下发指令模板（cmd 主题）
### 1. 手动一键清理
```json
{
  "seq": 10001,
  "action": "start_clean",
  "params": {},
  "timestamp": 1715556666
}
```

### 2. 停止清理
```json
{
  "seq": 10002,
  "action": "stop_clean",
  "params": {},
  "timestamp": 1715556688
}
```

### 3. 设置自动模式 / 定时
```json
{
  "seq": 10003,
  "action": "set_mode",
  "params": {
    "auto_mode": 1,
    "delay_min": 3
  },
  "timestamp": 1715556700
}
```

### 字段说明
- seq：消息序号，用于回执匹配
- action：指令动作码
- params：可变参数
- timestamp：时间戳

---

## 三、猫砂盆上报状态模板（status 主题）
```json
{
  "devId": "CL20260513001",
  "state": "cleaning",
  "weight": 3.8,
  "sand_full": 0,
  "fault": 0,
  "timestamp": 1715556720
}
```

### 状态 state 枚举
- `idle` 空闲待机
- `cleaning` 清理中
- `full` 砂已满
- `fault` 设备故障
- `cat_in` 猫咪在位

### 字段说明
- weight：猫咪重量 kg
- sand_full：0正常 1已满
- fault：0正常 1故障

---

## 四、设备回执应答模板（reply 主题）
```json
{
  "seq": 10001,
  "result": 1,
  "msg": "execute success"
}
```
- result：1成功 0失败
- seq 和 APP 下发的序号一致，APP 用来匹配回调

---

## 五、MQTT 关键配置（ESP32 直接用）
1. 心跳间隔：**60s**
2. QoS 等级：
   - 控制指令：**QoS1**（必须送达）
   - 状态上报：**QoS0**（丢包无所谓）
3. 清除会话：false，掉线保留订阅
4. 遗嘱消息：掉线自动上报离线状态
