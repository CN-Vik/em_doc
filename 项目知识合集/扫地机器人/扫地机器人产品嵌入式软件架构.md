一般**家用扫地机器人量产产品，大多数不直接跑 ROS**。
但**研发阶段、教学项目、实验室机器人、工业清洁机器人**，很多会用 ROS / ROS2。

可以这样理解：

## 1. 普通家用扫地机器人：通常不跑 ROS

比如石头、科沃斯、追觅、小米这类家用扫地机器人，内部一般是：

```text
MCU / SoC
 ├── 电机控制
 ├── 传感器采集
 ├── SLAM建图
 ├── 路径规划
 ├── 地图管理
 ├── App通信
 ├── OTA升级
 └── 清扫业务逻辑
```

它们大概率是自己定制的软件架构，可能跑：

```text
RTOS / Linux / 裸机 / 自研机器人框架
```

但不一定是 ROS。

原因是 ROS 对量产产品来说有几个问题：

```text
1. 资源占用偏大
2. 启动速度不一定最优
3. 实时性不如裸机/RTOS直接
4. 产品代码需要高度裁剪和稳定
5. 商业公司一般会做自研框架，方便量产维护
```

所以家用扫地机器人就算底层是 Linux，也可能是：

```text
Linux + 自研SLAM + 自研路径规划 + 自研通信框架
```

而不是：

```text
Linux + ROS
```

---

## 2. 研发/学习/原型机：很适合跑 ROS

如果你自己做扫地机器人、平衡车机器人、视觉机器人，用 ROS 很合适。

因为 ROS 已经帮你封装好了很多东西：

```text
传感器消息
坐标变换 TF
激光雷达数据
地图
导航
路径规划
可视化 RViz
仿真 Gazebo
SLAM算法接口
```

典型 ROS 架构是：

```text
雷达/相机/IMU/里程计
        ↓
    驱动节点
        ↓
    SLAM建图
        ↓
    定位导航
        ↓
    路径规划
        ↓
    运动控制
        ↓
  MCU控制电机
```

比如：

```text
ROS主控：RK3568 / 树莓派 / Jetson / 全志T527 / RV1126
MCU控制板：STM32 / GD32 / ESP32
```

主控跑 ROS，负责：

```text
建图、导航、路径规划、避障、App通信
```

MCU 负责：

```text
电机PWM
编码器采集
IMU采集
电池检测
风机控制
水泵控制
碰撞传感器
悬崖传感器
```

看目标。

如果你是**学习机器人算法**：

# 三、ROS 要不要用？

## 研发阶段：可以用

如果你们团队还没有导航经验，可以用：

```text
ROS2 + Nav2 + 激光雷达 + 轮速里程计
```

先把这些流程跑通：

```text
雷达数据
 ↓
里程计
 ↓
建图
 ↓
定位
 ↓
路径规划
 ↓

 ↓
MCU 控制左右轮
```

ROS2 当前官方仍有多个发行版，Jazzy Jalisco 支持到 2029 年，Kilted Kaiju 支持到 2026 年 12 月；如果现在新项目要用 ROS2 验证，优先选 Jazzy 这种支持周期长的版本。([ROS _docs][2])

## 量产阶段：不建议完整依赖 ROS

量产机不建议直接这样：

```text
开机启动一堆 ROS 节点
依赖一堆 Python 脚本
一堆 launch 文件
一堆 topic/service/action
```

原因是：

```text
启动慢
依赖复杂
调试链路长
系统资源占用大
售后定位问题麻烦
量产裁剪困难
```

更推荐量产时变成：

```text
Linux C/C++ 进程
 ├── slam_service
 ├── nav_service
 ├── map_service
 ├── app_service
 ├── ota_service
 └── mcu_comm_service
```

ROS 只是前期帮你验证算法和流程，后面把成熟部分裁剪成产品框架。

# 五、Linux 和 MCU 通信协议怎么设计

主控 Linux 不应该直接控制 PWM。
它应该发“目标速度”给 MCU。

例如 Linux 发：

```c
typedef struct
{
    int16_t linear_mm_s;   // 前进后退速度，单位 mm/s
    int16_t angular_mrad_s;// 旋转角速度，单位 mrad/s
    uint8_t mode;          // 控制模式
} chassis_cmd_t;
```

MCU 回：

```c
typedef struct
{
    int16_t left_speed_mm_s;    // 左轮实际速度
    int16_t right_speed_mm_s;   // 右轮实际速度
    int32_t left_encoder;       // 左轮编码器累计值
    int32_t right_encoder;      // 右轮编码器累计值
    uint16_t battery_mv;        // 电池电压
    uint16_t fault_code;        // 故障码
    uint8_t bumper_state;       // 碰撞状态
    uint8_t cliff_state;        // 悬崖状态
} chassis_status_t;
```

主控只管：

```text
我要你以多少速度走
我要你左转/右转
我要你停止
我要你开始清扫
我要你回充
```

MCU 负责：

```text
PWM输出
PID闭环
编码器测速
堵转保护
过流保护
悬崖急停
碰撞急停
低电保护
```

# 1. 第一版做出来后，先不要急着加功能

很多公司容易犯一个错误：

```text
第一版刚跑通
↓
马上加地图、加AI、加语音、加自动集尘、加拖布升降
↓

↓
底层不稳定
↓
```

正确做法应该是：


第一版后期最重要的是这几件事：

```text

5. 会不会漏扫
6. 会不会误报故障
7. 会不会电机堵转烧板

9. 用户 App 操作是否顺手
10. 售后能不能定位问题
```

# 2. 后期第一步：做“稳定性闭环”

你们要先建立一套测试体系。

## 一、整机老化测试

比如：

```text
连续运行 24 小时
连续运行 72 小时
连续清扫 100 次
连续回充 100 次
低电自动回充 100 次
碰撞避障 1000 次
悬崖检测 1000 次
尘盒插拔 500 次
风机启停 1000 次
滚刷堵转恢复 500 次
```

目标是把隐藏问题逼出来。

比如你们可能会遇到：

```text
运行几个小时后 MCU 死机
Linux 主控内存泄漏
电机 PID 偶发失控
雷达数据偶发丢失
地图保存失败
低电回充失败
尘盒检测误触发
轮子打滑导致定位漂移
```

这些都要在实验室阶段暴露出来，不要等用户买回家再暴露。

---

# 3. 第二步：把日志系统做好

扫地机器人后期最需要的是**故障追踪能力**。

你们 MCU 和 Linux 都要有日志。

## MCU 日志建议

MCU 里面至少要记录：

```text
系统复位原因
上一次故障码
电机过流
电机堵转
风机堵转
滚刷堵转
边刷堵转
悬崖触发
碰撞触发
电池低压
充电异常
通信超时
看门狗复位
```

可以存到 Flash 里面。

你之前做猫砂盆 `ERROR` 日志存 Flash 的思路，在扫地机器人里也很适合。

建议设计成：

```c
typedef enum
{
    ROBOT_ERR_NONE = 0,
    ROBOT_ERR_LEFT_WHEEL_BLOCK,
    ROBOT_ERR_RIGHT_WHEEL_BLOCK,
    ROBOT_ERR_BRUSH_BLOCK,
    ROBOT_ERR_FAN_OVER_CURRENT,
    ROBOT_ERR_CLIFF_TRIGGER,
    ROBOT_ERR_BAT_LOW,
    ROBOT_ERR_CHARGE_FAIL,
    ROBOT_ERR_MCU_WDG_RESET,
    ROBOT_ERR_SOC_COMM_TIMEOUT,
} robot_error_t;
```

然后保存：

```c
typedef struct
{
    uint32_t timestamp;
    uint16_t error_code;
    uint16_t motor_current;
    uint16_t battery_mv;
    uint16_t left_speed;
    uint16_t right_speed;
    uint8_t  work_state;
    uint8_t  reset_reason;
} robot_error_log_t;
```

这样售后看到故障，不是猜，而是能查：

```text
什么时候出错
当时什么状态
电池多少电
电机电流多少
轮子速度多少
是不是看门狗复位
是不是通信超时
```

---

# 4. 第三步：把状态机重新梳理清楚

第一版能跑，很多时候代码是“堆出来的”。

后期一定要整理成明确状态机。

扫地机器人主状态机可以这样：

```text
ROBOT_STATE_IDLE              待机
ROBOT_STATE_CLEANING          清扫中
ROBOT_STATE_PAUSE             暂停
ROBOT_STATE_DOCKING           回充中
ROBOT_STATE_CHARGING          充电中
ROBOT_STATE_ERROR             故障
ROBOT_STATE_OTA               升级中
ROBOT_STATE_FACTORY_TEST      产测模式
```

状态切换要清晰：

```text
待机
 ↓ 开始清扫
清扫中
 ↓ 电量低
回充中
 ↓ 找到充电座
充电中
 ↓ 充满
待机
```

异常状态也要清晰：

```text
清扫中
 ↓ 轮子堵转
故障
 ↓ 用户处理
待机
```

不要到处写：

```c
if (xxx)
{
    motor_stop();
    fan_stop();
    brush_stop();
    set_state(...);
}
```

后期应该封装成：

```c
robot_state_set(ROBOT_STATE_ERROR, ROBOT_ERR_LEFT_WHEEL_BLOCK);
```

这样代码才好维护。

---

# 5. 第四步：把 MCU 和 Linux 的协议固化

第一版很多协议可能比较临时，比如：

```text
发一个速度
回一个状态
临时加一个故障码
临时加一个传感器字段
```

后期要正式设计协议版本。

建议你们通信协议里面加：

```text
帧头
协议版本
命令字
数据长度
序号
payload
CRC
```

例如：

```c
typedef struct
{
    uint8_t  head1;       // 0xAA
    uint8_t  head2;       // 0x55
    uint8_t  version;     // 协议版本
    uint8_t  cmd;         // 命令字
    uint16_t seq;         // 序号
    uint16_t len;         // 数据长度
    uint8_t  payload[64]; // 数据
    uint16_t crc;         // 校验
} robot_frame_t;
```

为什么要有版本号？

因为后期一定会遇到：

```text
V1.0 MCU 固件
V1.1 Linux 固件
V1.2 App 协议
V2.0 新增传感器
```

如果没有版本管理，后面升级会很乱。

---

# 6. 第五步：做 OTA 升级体系

后期产品一定要支持 OTA。

而且最好是：

```text
Linux 主控可以 OTA
MCU 也可以 OTA
```

架构可以是：

```text
云端/App
  ↓
Linux 主控下载固件
  ↓
Linux 自己升级
  ↓
Linux 通过 UART/CAN 给 MCU 升级
  ↓
MCU Bootloader 写入新固件
```

MCU 这边建议至少支持：

```text
固件版本号
固件 CRC 校验
升级失败回滚
升级进度上报
升级超时保护
Bootloader 强制恢复
```

如果没有 OTA，后期售后成本会非常高。

---

# 7. 第六步：做量产测试模式

公司产品后期最容易忽略的是产测。

你们需要一个**工厂测试模式**。

比如通过串口/按键/App 进入：

```text
FACTORY_TEST_MODE
```

测试项目包括：

```text
左轮正转
左轮反转
右轮正转
右轮反转
风机测试
滚刷测试
边刷测试
水泵测试
碰撞开关测试
悬崖传感器测试
尘盒检测
雷达通信测试
充电触点检测
电池电压检测
WiFi测试
按键测试
蜂鸣器测试
LED测试
```

每个测试都返回：

```text
PASS / FAIL
具体数值
故障原因
```

比如：

```text
LEFT_WHEEL_TEST: PASS, speed=320mm/s, current=180mA
FAN_TEST: FAIL, current=0mA
CLIFF_TEST: PASS, adc=2300
BATTERY_TEST: PASS, voltage=15800mV
```

没有产测模式，量产会非常痛苦。

---

# 8. 第七步：优化用户体验

稳定之后再优化体验。

用户体验包括：

```text
清扫路线是否合理
是否漏扫
是否重复扫太多
是否容易卡住
声音是否太大
回充是否可靠
App 操作是否简单
故障提示是否清楚
清扫完成是否有明确提示
地图是否好看
```

不要只从工程师角度看产品。

工程师可能觉得：

```text
功能都实现了
```

但用户在意的是：

```text
好不好用
麻不麻烦
会不会经常出问题
出了问题知不知道怎么处理
```

比如故障提示：

不好的提示：

```text
ERROR 0x23
```

好的提示：

```text
左轮被卡住，请检查左轮是否缠绕毛发
```

# 9. 第八步：成本优化

产品稳定后，开始降成本。

可以优化：

```text
MCU型号
电机驱动芯片
传感器数量
结构件
电池容量
充电方案
雷达方案
WiFi模组
PCB层数
线束数量
接口数量
```

但是注意：

**不要第一版就疯狂降成本。**

正确顺序是：

```text
先做稳定
再降成本
```

否则很容易出现：

```text
便宜传感器误判
低成本电机寿命差
电源余量不够
电机驱动发热
ADC采样漂移
充电不稳定
```

# 11. 对你嵌入式软件来说，后期最该关注什么

你作为 MCU / 嵌入式软件开发，后期重点是这几块：

```text
1. 电机控制稳定性
2. 传感器抗干扰
3. 故障保护
4. MCU 与 Linux 通信可靠性
5. Bootloader 和 OTA
6. 日志系统
7. 产测模式
8. 低功耗和充电管理
9. 看门狗和异常恢复
10. 软件分层和状态机重构
```

你不要只盯着“功能能不能跑”。

你要盯：

```text
异常情况下会不会安全停机
通信断了怎么办
电机堵了怎么办
电池低压怎么办
升级失败怎么办
传感器坏了怎么办
用户乱操作怎么办
系统死机能不能恢复
```

这才是产品化嵌入式开发的重点。

# 12. 最推荐的后期路线

我建议你们这样走：

```text
第 1 步：冻结第一版功能
第 2 步：集中修 Bug 和稳定性
第 3 步：补日志、故障码、产测模式
第 4 步：完善 OTA
第 5 步：小批量试产
第 6 步：收集真实用户问题
第 7 步：优化清扫体验和回充体验
第 8 步：再做新功能
第 9 步：做成本优化
第 10 步：规划 V2 智能导航版本
```

千万不要：

```text
第一版刚出来就疯狂加功能
```

应该先：

```text
把第一版打磨成稳定可卖的产品
```

---

# 13. 一句话总结

**扫地机器人第一版做出来后，后期不是马上加 ROS、AI、视觉、SLAM，而是先做稳定性、日志、故障保护、OTA、产测、量产一致性和用户体验。**

对公司来说：

```text
第一版：解决“能不能做出来”
后期：解决“能不能稳定卖出去”
量产：解决“能不能低成本、低售后、大批量卖出去”
```
