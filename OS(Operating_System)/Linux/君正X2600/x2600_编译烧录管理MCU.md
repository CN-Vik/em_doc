你这个 `libmcu` 目录就是 **X2600 的 MCU 小核工程**。X2600 不是传统单 MCU，它是多核异构芯片，公开资料里写的是 **XBurst2 计算核 + Victory0/RISC-V 控制核 + XBurst0** 这类结构；你这个 `libmcu` 大概率就是给里面的 **RISC-V 小核/实时控制核** 编译固件用的。([英伟达][1])

你现在目录里已经有这些产物：

```bash
libmcu-bare.elf
libmcu-bare.bin
libmcu-bare.map
```

说明这个工程以前已经成功编译过一次。

---

## 1. 先理解这个目录是干啥的

你这个目录可以这样理解：

```bash
libmcu/
├── Makefile              # 真正控制怎么编译的核心文件
├── buildmcu.sh           # 编译脚本，通常封装 make
├── build-cp.sh           # 编译后拷贝固件到系统 output/rootfs
├── mcu_boot.sh           # Linux 起来后启动/加载 MCU 小核固件的脚本
├── Config.in             # IConfig / Kconfig 配置入口
├── config.h              # 当前配置生成/保存的头文件
├── configs               # 不同板型/方案的默认配置
├── devices               # 设备层，比如板级设备、外设抽象
├── drivers               # MCU 小核驱动
├── include               # 公共头文件
├── os                    # bare-metal 或 RTOS 相关代码
├── soc                   # X2600/RISC-V 小核 SoC 相关代码
├── vendor                # 厂商代码
├── example               # 示例程序
├── lib                   # 静态库或预编译库
├── tools                 # 编译/打包相关工具
└── libmcu-bare.bin       # 最终给小核运行的裸机 bin
```

官方 X2600 文档片段也提到：小核工程目录在 `<工程目录>/libmcu`，并且可以用 VS Code 打开这个目录；小核相关测试里还提到 JTAG 连接和固件烧录流程。([Ingenic文档][2])

# 2. 怎么编译？

你先不要手动乱敲 `make`，先看脚本。因为君正 SDK 一般会把工具链路径、配置、输出路径都封装在脚本里。

进入目录：

```bash
cd ~/project/x2600/libmcu
```

先看脚本内容：

```bash
sed -n '1,200p' buildmcu.sh
sed -n '1,200p' Makefile
```

再看它用什么编译器：

```bash
grep -R "CROSS_COMPILE\|riscv\|gcc\|CC\s*=" -n Makefile buildmcu.sh config.h configs 2>/dev/null
```

重点看有没有类似：

```makefile
riscv-none-embed-gcc
riscv64-unknown-elf-gcc
riscv32-unknown-elf-gcc
```

因为这个小核大概率是 RISC-V 控制核，不是 Linux 大核的 MIPS 应用程序。

---

## 推荐编译方式

大概率直接执行：

```bash
chmod +x buildmcu.sh
./buildmcu.sh
```

如果脚本里面只是封装 `make`，也可能可以这样：

```bash
make clean
make -j$(nproc)
```

编译成功后，一般会重新生成：

```bash
libmcu-bare.elf
libmcu-bare.bin
libmcu-bare.map
```

其中：

| 文件                | 作用                     |
| ----------------- | ---------------------- |
| `libmcu-bare.elf` | 带符号表的调试文件，JTAG/GDB 调试用 |
| `libmcu-bare.bin` | 真正给 MCU 小核加载/烧录的裸二进制固件 |
| `libmcu-bare.map` | 链接映射文件，排查地址、函数、变量占用空间用 |

你现在目录里已经有这三个文件，所以编译目标应该就是生成它们。

# 3. 如果提示找不到编译器怎么办？

例如报错：

```bash
riscv-none-embed-gcc: command not found
```

那就是工具链 PATH 没配好。

你可以查 Makefile 需要哪个工具链：

```bash
grep -R "riscv.*gcc\|CROSS_COMPILE" -n .
```

然后在整个 SDK 里找工具链：

```bash
cd ~/project/x2600
find tools -name "*gcc*" | grep -i riscv
```

假如找到类似：

```bash
~/project/x2600/tools/toolchains/riscv/bin/riscv-none-embed-gcc
```

那就临时加到 PATH：

```bash
export PATH=~/project/x2600/tools/toolchains/riscv/bin:$PATH
```

然后验证：

```bash
which riscv-none-embed-gcc
riscv-none-embed-gcc -v
```

再回去编译：

```bash
cd ~/project/x2600/libmcu
./buildmcu.sh
```

注意：你之前加过的这个：

```bash
export PATH=/home/vik/project/x2600/tools/toolchains/mips-xburst2-gcc720-glibc238/bin:$PATH
```

这个更像是给 **Linux 大核 MIPS 用户态/内核** 编译用的，不一定是给 `libmcu` 小核用的。`libmcu` 如果是 RISC-V 小核，就要找 RISC-V 工具链。

# 4. 怎么烧录 / 加载 MCU 小核代码？

这里通常有两种方式。

---

## 方式一：整包烧录

也就是把 `libmcu-bare.bin` 打包进整个 X2600 固件里，然后用君正 USB 烧录工具烧到板子。

大流程是：

```bash
cd ~/project/x2600/libmcu
./buildmcu.sh
./build-cp.sh
```

然后回到 SDK 顶层或者 `build` 目录：

```bash
cd ~/project/x2600/build
```

再重新打包整个系统固件。

具体打包命令要看你们 SDK 的 `README` 或 `build/Makefile`，可以先查：

```bash
cd ~/project/x2600/build
ls
sed -n '1,200p' README
sed -n '1,160p' Makefile
```

一般最终固件会在类似这些目录：

```bash
~/project/x2600/build/output/
~/project/x2600/output/
```

官方公开资料也提到 X2600 开发包包含 Linux kernel、U-Boot、Buildroot、编译工具链和 USB Flash 烧录工具。([longsto.com][3])

---

## 方式二：Linux 启动后动态加载小核固件

你目录里有：

```bash
mcu_boot.sh
S39mcu_start_up
S99mlx
```

这几个很关键。

它们大概率是 Linux 系统启动后，用脚本把 `libmcu-bare.bin` 加载到小核，然后启动小核。

你先看脚本：

```bash
cd ~/project/x2600/libmcu
sed -n '1,200p' mcu_boot.sh
sed -n '1,200p' S39mcu_start_up
sed -n '1,200p' S99mlx
```

如果里面有类似：

```bash
/sys/class/remoteproc/remoteproc0/firmware
/sys/class/remoteproc/remoteproc0/state
```

那就是 Linux 通过 `remoteproc` 启动小核。

典型流程类似这样：

```bash
echo stop > /sys/class/remoteproc/remoteproc0/state
cp libmcu-bare.bin /lib/firmware/
echo libmcu-bare.bin > /sys/class/remoteproc/remoteproc0/firmware
echo start > /sys/class/remoteproc/remoteproc0/state
```

但是你不要直接照抄，先看你自己的 `mcu_boot.sh`，因为不同君正 SDK 路径可能不一样。

# 5. 怎么添加 `.c` 文件？

这个要看 `Makefile` 的组织方式。一般有三种。

---

## 情况一：Makefile 自动搜索所有 `.c`

如果 Makefile 里有类似：

```makefile
SRCS += $(wildcard drivers/*.c)
SRCS += $(wildcard example/*.c)
SRCS += $(wildcard devices/*.c)
```

那你只要把 `.c` 放进对应目录即可。

比如你要加一个 LED 模块：

```bash
mkdir -p app
touch app/my_led.c
touch include/my_led.h
```

然后如果 Makefile 自动搜索 `app/*.c`，就不用改 Makefile。

但如果没有搜索 `app`，就要加进去。

---

## 情况二：Makefile 明确列出每个 `.c`

比如 Makefile 里有：

```makefile
SRCS += example/main.c
SRCS += drivers/uart.c
SRCS += drivers/gpio.c
```

那你添加：

```bash
app/my_led.c
```

之后，就要在 Makefile 加：

```makefile
SRCS += app/my_led.c
```

---

## 情况三：用 `obj-y` 风格

有些嵌入式工程会这样：

```makefile
obj-y += drivers/gpio.o
obj-y += example/main.o
```

那你加 `.c` 时，要写成 `.o`：

```makefile
obj-y += app/my_led.o
```

不是：

```makefile
obj-y += app/my_led.c
```

---

# 6. 怎么添加 `.h` 文件？

`.h` 文件本身不会单独编译，它是被 `.c` 文件 `#include` 进去的。

推荐放这里：

```bash
libmcu/include/
```

比如：

```bash
include/my_led.h
app/my_led.c
```

`my_led.h`：

```c
#ifndef __MY_LED_H__
#define __MY_LED_H__

void my_led_init(void);
void my_led_on(void);
void my_led_off(void);

#endif
```

`my_led.c`：

```c
#include "my_led.h"

void my_led_init(void)
{
    // 初始化 GPIO
}

void my_led_on(void)
{
    // 拉高/拉低 GPIO
}

void my_led_off(void)
{
    // 拉高/拉低 GPIO
}
```

然后在 `main.c` 或你的入口文件里：

```c
#include "my_led.h"

int main(void)
{
    my_led_init();

    while (1) {
        my_led_on();
        // delay
        my_led_off();
        // delay
    }
}
```

---

## 如果编译提示找不到头文件

比如：

```bash
fatal error: my_led.h: No such file or directory
```

说明 Makefile 没有把 `include/` 加到头文件搜索路径。

你要在 Makefile 里找类似：

```makefile
CFLAGS += -Iinclude
```

如果没有，加上：

```makefile
CFLAGS += -I$(TOPDIR)/include
```

或者简单点：

```makefile
CFLAGS += -Iinclude
```

如果你的头文件放在 `app/include`，那还要加：

```makefile
CFLAGS += -Iapp/include
```

---

# 7. 推荐你这样加自己的应用代码

不要直接把代码乱塞进 `drivers/`、`soc/`、`vendor/`，这些一般是底层代码。

建议新建一个自己的应用目录：

```bash
cd ~/project/x2600/libmcu

mkdir -p app
mkdir -p app/include
```

结构变成：

```bash
libmcu/
├── app
│   ├── my_led.c
│   ├── my_task.c
│   └── include
│       ├── my_led.h
│       └── my_task.h
├── drivers
├── soc
├── os
├── include
└── Makefile
```

然后 Makefile 里加：

```makefile
CFLAGS += -Iapp/include

SRCS += app/my_led.c
SRCS += app/my_task.c
```

如果是 `obj-y` 风格：

```makefile
obj-y += app/my_led.o
obj-y += app/my_task.o
```

# 8. 你应该先找真正的入口函数

你要知道程序从哪里开始跑。

在 `libmcu` 目录搜：

```bash
grep -R "int main\|void main\|main(void)" -n .
```

也可以搜启动文件：

```bash
grep -R "Reset_Handler\|_start\|entry" -n soc os vendor example .
```

常见情况是：

```bash
example/main.c
```

或者：

```bash
os/bare/main.c
```

或者某个 demo 文件。

你找到入口后，先不要新建一堆东西，先在入口里加一句日志或者 GPIO 翻转，确认你编译和加载的是你改过的代码。

例如：

```c
printf("hello libmcu app\r\n");
```

或者用板子上 LED/GPIO 验证。

你可以按这个顺序来：

cd ~/project/x2600/libmcu

sed -n '1,200p' buildmcu.sh

然后根据脚本操作。不要盲目执行，先看它里面路径对不对。

# 10. 你现在最应该执行这几个命令

把结果发我，我就能直接判断你的工程该怎么加文件、怎么编译：

```bash
cd ~/project/x2600/libmcu

sed -n '1,200p' buildmcu.sh
sed -n '1,240p' Makefile
grep -R "int main\|void main" -n . | head -20
grep -R "CROSS_COMPILE\|riscv\|gcc\|SRCS\|obj-y\|CFLAGS\|INCLUDE" -n Makefile buildmcu.sh configs config.h | head -100
```

你这个工程的核心判断点就三个：

```text
1. buildmcu.sh 里面到底怎么调用 make
2. Makefile 里面怎么收集 .c 文件
3. mcu_boot.sh 里面怎么把 libmcu-bare.bin 加载到小核
```

搞清楚这三个，后面添加 `.c/.h`、编译、烧录就非常清楚了。
