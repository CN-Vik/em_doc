现在已经不是“加载 KO”的问题了，**已经走到真正和 BMI160 芯片通信这一步了**。

关键日志是这个：

```text
bmi160_spi spi0.0: Wrong chip id, got 0 expected d1
```

意思是：

```text
驱动已经匹配到 spi0.0
bmi160_spi.ko 已经开始 probe
驱动去读 BMI160 的 CHIP_ID 寄存器
期望读到 0xD1
实际读到 0x00
所以 probe 失败，不会生成 /sys/bus/iio/devices/iio:device0
```

所以 `/sys/bus/iio/devices/` 为空是正常的，因为 probe 已经被 `Wrong chip id` 中断了。

---

## 当前状态总结

你现在已经成功了这些：

```text
utils.ko              OK
soc_spi.ko            OK
/sys/class/spi_master/spi0 已出现
bmi160_core.ko        OK
bmi160_spi.ko         OK
bmi160_spi_board.ko   OK
/sys/bus/spi/devices/spi0.0 已出现
```

失败点只剩：

```text
SPI 真实通信失败，BMI160 ID 读成了 0x00
```

这通常不是 IIO 驱动框架问题，而是下面这些之一：

```text
1. CS 引脚 PD05 不对
2. SPI0 的 CLK/MOSI/MISO 引脚和硬件接线不一致
3. MOSI/MISO 接反
4. BMI160 没供电，或者 VDD/VDDIO 不对
5. SPI mode 不对，当前是 MODE_0，可以试 MODE_3
6. SPI 频率仍然偏高，先降到 100k 或 500k
7. 实际芯片不是 BMI160，或者芯片损坏
8. CS 没有真正拉低，BMI160 没被选中
```

`vdd not found, using dummy regulator` 和 `mounting matrix not found` 暂时不是致命问题；真正致命的是 `Wrong chip id, got 0 expected d1`。

## 1. 先确认你的四根 SPI 线

你现在软件配置是：

```text
SPI0_CLK  = PD00
SPI0_MOSI = PD01
SPI0_MISO = PD02
BMI160_CS = PD05
```

所以硬件必须对应：

```text
X2600 PD00  -> BMI160 SCK/SCL
X2600 PD01  -> BMI160 SDI/MOSI/SDA
X2600 PD02  -> BMI160 SDO/MISO/SA0
X2600 PD05  -> BMI160 CSB
GND         -> GND
VDD/VDDIO   -> 正确电压
```

重点查 **MOSI/MISO 有没有接反**。如果 MISO 没接上或者一直低，驱动读 ID 就很容易得到 `0x00`。

---

## 2. 用 spidev 手动读 BMI160 ID

先把 BMI160 驱动卸掉，避免占用 `spi0.0`：

```sh

```

然后加载 spidev：

```sh

insmod spidev.ko 2>/dev/null
```

添加 SPI 设备，CS 用你的 PD05：

```sh

```

看有没有生成：

```sh
ls -l /dev/spidev*
ls -l /sys/bus/spi/devices/
```

然后先设置低速 MODE_0：

```sh
cmd_spi set /dev/spidev0.0 mode=0x00 speed=100000 bits=8 lsb=0
cmd_spi info /dev/spidev0.0
```

读 BMI160 chip id。BMI160 的 CHIP_ID 寄存器是 `0x00`，SPI 读一般要把最高位置 1，所以发送：

```sh
cmd_spi transfer /dev/spidev0.0 0x80 0x00
```

你要重点看返回的第二个字节。理想应该类似：

```text
receive[0]: xx
receive[1]: d1
```

如果第二个字节还是：

```text

```

说明不是 BMI160 Linux 驱动问题，而是底层 SPI 通信/接线/片选/供电问题。

## 4. 用示波器/逻辑分析仪看四根线

你现在已经能触发 probe，所以加载 `bmi160_spi_board.ko` 时，驱动一定会尝试 SPI 读 ID。这个时候用示波器看：

```text
PD05 CS   是否被拉低
PD00 CLK  是否有时钟
PD01 MOSI 是否发出 0x80
PD02 MISO 是否有返回数据
```

判断非常直接：

```text
CS 没动：CS 配置/PD05 错
CLK 没动：SPI master/引脚复用不对
MOSI 没动：MOSI 配置不对
MISO 一直 0：芯片没响应、没供电、MISO 接错、CS 错、mode 错
MISO 一直 1：MISO 悬空/上拉/芯片没响应
```

你现在读到 `0x00`，尤其要重点看 **MISO 是不是一直低**。

# 君正 X2600N 加载 BMI160 SPI IMU 驱动调试教程

## 0. 最终目标

目标是在 X2600N 上通过 SPI0 挂载 BMI160 IMU，并让 Linux IIO 框架生成：

```bash
/sys/bus/iio/devices/iio:device0
```

最终可以读：

```bash
cat /sys/bus/iio/devices/iio:device0/name

cat /sys/bus/iio/devices/iio:device0/in_accel_x_raw
cat /sys/bus/iio/devices/iio:device0/in_accel_y_raw
cat /sys/bus/iio/devices/iio:device0/in_accel_z_raw

cat /sys/bus/iio/devices/iio:device0/in_anglvel_x_raw
cat /sys/bus/iio/devices/iio:device0/in_anglvel_y_raw
cat /sys/bus/iio/devices/iio:device0/in_anglvel_z_raw
```

你的硬件设定目前是：

```text
SPI0_CLK  = PD00
SPI0_MOSI = PD01
SPI0_MISO = PD02
BMI160_CS = PD05
```

所以软件链路是：

```text
utils.ko
    ↓

    ↓
注册 /sys/class/spi_master/spi0
    ↓
bmi160_spi_board.ko
    ↓
注册 /sys/bus/spi/devices/spi0.0
    ↓

    ↓
读取 BMI160 chip id
    ↓
bmi160_core.ko
    ↓
注册 IIO 设备
```

# 1. 先理解君正 X2600 这套驱动体系

X2600 这套工程不是纯标准 Linux DTS 驱动玩法，而是：

```text
Linux kernel .config
        +
device tree
        +
君正 module_driver
        +
IConfigTool 生成的 MD_XXX 配置
        +
启动脚本/手动 insmod 参数
```

你看到的这个文件：

```bash
build/configs/x2600n_tiger_nor_5.10_defconfig
```

不是 Linux 设备树，也不是内核 `.config`，它是君正工程的总配置文件。

里面有：

```bash
APP_kernel_config=x2600_evb_module_base_linux_sfc_nor_defconfig
APP_module_driver=y
MD_INIT_ORDER_FILE=package/default_driver_init_order.mk
MD_INIT_START_FILE=package/S11module_driver_default
```

含义大概是：

```text
APP_kernel_config
    选择真正的 Linux kernel defconfig

APP_module_driver=y
    启用君正 module_driver 体系

MD_XXX
    控制 module_driver 编译哪些模块、模块启动时使用哪些参数
```

你板子上其实有 device tree，因为之前能看到：

```bash
/sys/firmware/devicetree/base/apb/spi@0x10043000
/sys/firmware/devicetree/base/apb/spi@0x10044000
/sys/firmware/devicetree/base/aliases/spi0
/sys/firmware/devicetree/base/aliases/spi1
```

但是 **SPI0 master 实际注册出来，是靠君正 `soc_spi.ko` 这个 module_driver 模块完成的**。

君正官方 SPI 文档也说明，需要在 IConfigTool 里进入“模块化驱动/驱动”，根据使用 SPI 控制器驱动还是 GPIO_SPI 驱动做配置；如果 SPI 控制器驱动不正常，可以用 GPIO_SPI 验证硬件/IO 是否有问题。

# 5. BMI160 板级注册模块的作用

`bmi160_core.ko` 和 `bmi160_spi.ko` 是 Linux 已有的 BMI160 驱动。

但是它们不会自己知道：

```text
BMI160 接在哪个 SPI 总线？
CS 是哪个 GPIO？
SPI mode 是多少？
频率是多少？
```

所以你需要一个板级注册模块：

```bash
module_driver/bmi160_spi_board/bmi160_spi_board.ko
```

它的作用是：

```text
告诉 Linux：
SPI0 上有一个设备
名字叫 "bmi160"
CS 是 PD05
chip_select 是 0
mode 是 SPI_MODE_0 或 SPI_MODE_3
```

核心结构大概是：

```c
static struct spi_board_info bmi160_spi_board_info = {
    .modalias = "bmi160",
    .max_speed_hz = 1 * 1000 * 1000,
    .mode = SPI_MODE_0,
    .chip_select = 0,
    .controller_data = (void *)GPIO_PD(5),
};
```

这里最容易混淆：

```text
.chip_select = 0
```

不是 PD00，也不是 PD05。它的意思是创建：

```text
spi0.0
```

而：

```text
.controller_data = GPIO_PD(5)
```

才是真正的 CS GPIO。

君正官方 SPI 文档中的驱动层接口也是类似思路：先用 `spi_busnum_to_master()` 找到 SPI master，再通过 `spi_new_device()` 注册 SPI 设备；如果 master 不存在，注册设备会失败。

# 8. 你一路踩过的坑

## 坑 1：直接加载 `bmi160_core.ko` 报 unknown symbol

现象：

```text
bmi160_core: Unknown symbol devm_iio_triggered_buffer_setup
```

原因：

```text
bmi160_core.ko 依赖 IIO triggered buffer 模块
你直接 insmod bmi160_core.ko，依赖没有先加载
```

解决：

```sh
insmod kfifo_buf.ko
insmod industrialio-triggered-buffer.ko
insmod bmi160_core.ko
```

你当时日志里明确出现了 `devm_iio_triggered_buffer_setup` 缺失，后续又因为 `bmi160_core.ko` 没加载成功导致 `bmi160_spi.ko` 缺 `bmi160_regmap_config` 和 `bmi160_core_probe`。

---

## 坑 2：`bmi160_spi.ko` 报 unknown symbol

现象：

```text
bmi160_spi: Unknown symbol bmi160_regmap_config
bmi160_spi: Unknown symbol bmi160_core_probe
```

原因：

```text
bmi160_spi.ko 依赖 bmi160_core.ko
但是 bmi160_core.ko 因为 IIO 依赖没加载而失败
```

解决顺序：

```sh
insmod kfifo_buf.ko
insmod industrialio-triggered-buffer.ko
insmod bmi160_core.ko
insmod bmi160_spi.ko
```

## 坑 3：`bmi160_spi_board.ko` 报 No such device

现象：

```text
bmi160_spi_board: failed to get spi master 0
```

原因：

```text
系统中没有 /sys/class/spi_master/spi0
也就是 X2600 普通 SPI0 master 没有注册
```

解决：

先加载：

```sh
insmod utils.ko
insmod soc_spi.ko ...
```

让：

```sh
ls /sys/class/spi_master/
```

出现：

```text
spi0
```

然后再加载 `bmi160_spi_board.ko`。

## 坑 4：只看到 SFC，不代表普通 SPI 已经起来

你一开始 `dmesg` 里看到：

```text
ingenic-sfc 13440000.sfc: SPI NOR MTD LOAD OK
```

这个是 SPI NOR Flash 的 SFC 控制器，不是普通 SPI master。

BMI160 需要的是：

```text
/sys/class/spi_master/spi0
```

所以看到 SFC 日志没有意义，必须看：

```sh
ls /sys/class/spi_master/
```

## 坑 5：`soc_spi.ko` 依赖 `utils.ko`

现象：

```text
soc_spi: Unknown symbol param_gpio_ops
soc_spi: Unknown symbol gpio_to_str
soc_spi: Unknown symbol __assert
soc_spi: Unknown symbol gpio_set_func
```

原因：

```text
soc_spi.ko 依赖 utils.ko
```

你用 `nm` 查到这些符号都由 `module_driver/output/utils.ko` 提供，`modinfo soc_spi.ko` 也显示 `depends: utils`。

解决：

```sh
insmod utils.ko
insmod soc_spi.ko ...
```

## 坑 6：手动 `insmod soc_spi.ko` 不会自动吃 IConfig 参数

IConfig 里虽然配了：

```text
MD_X2600_510_SPI0_CLK=PD00
MD_X2600_510_SPI0_MISO=PD02
MD_X2600_510_SPI0_MOSI=PD01
```

但是你手动执行：

```sh
insmod soc_spi.ko spi0_is_enable=1
```

它不会自动读取 `build/.config.in`。

所以它使用默认值，导致日志：

```text
SPI spi0_clk(PA00) is invaild!
```

# 9. 当前剩余问题的排查方法

## 9.1 确认硬件接线

当前软件配置：

```text
X2600 PD00 -> BMI160 SCK/SCL
X2600 PD01 -> BMI160 SDI/MOSI/SDA
X2600 PD02 -> BMI160 SDO/MISO/SA0
X2600 PD05 -> BMI160 CSB
GND        -> GND
VDD/VDDIO  -> 正确电压
```

重点检查：

```text
1. MOSI/MISO 有没有接反
2. CS 是否真的是 PD05
3. BMI160 VDD/VDDIO 是否有电
4. BMI160 是否进入 SPI 模式
5. PD00/PD01/PD02 是否确实接到了 BMI160
```

---

## 9.2 用 cmd_spi 手动读 chip id

先卸载 BMI160，避免占用 `spi0.0`：

```sh
cd /tmp/kernel_drv_mode

rmmod bmi160_spi_board 2>/dev/null
rmmod bmi160_spi 2>/dev/null
rmmod bmi160_core 2>/dev/null
```

加载 spidev：

```sh
insmod spidev_helper.ko 2>/dev/null
insmod spidev.ko 2>/dev/null
```

添加 spidev 设备：

```sh
cmd_spi add_dev 0 pd05
```

设置 MODE_0、低速：

```sh
cmd_spi set /dev/spidev0.0 mode=0x00 speed=100000 bits=8 lsb=0
cmd_spi info /dev/spidev0.0
```

BMI160 的 CHIP_ID 寄存器地址是 `0x00`，SPI 读一般需要地址最高位置 1，所以读命令是：

```sh
cmd_spi transfer /dev/spidev0.0 0x80 0x00
```

期望返回：

```text
receive[1]: d1
```

如果返回：

```text
receive[1]: 00
```

说明不是 IIO/BMI160 驱动代码问题，而是 SPI 通信本身没有成功。

君正官方文档里也提供了 `cmd_spi add_dev`、`cmd_spi transfer`、`cmd_spi set`、`cmd_spi info` 这套用户态 SPI 测试方法。

---

## 9.3 试 MODE_3

如果 MODE_0 读不到，试 MODE_3：

```sh
cmd_spi set /dev/spidev0.0 mode=0x03 speed=100000 bits=8 lsb=0
cmd_spi transfer /dev/spidev0.0 0x80 0x00
```

如果 MODE_3 能读到 `0xD1`，修改 `bmi160_spi_board.c`：

```c
.mode = SPI_MODE_3,
```

然后重新编译推送：

```bash
cd ~/project/x2600/module_driver/bmi160_spi_board
make clean
make V=1

adb push bmi160_spi_board.ko /tmp/kernel_drv_mode/
```

---

## 9.4 降低 SPI 频率

调试阶段建议：

```c
.max_speed_hz = 100 * 1000,
```

也就是 100 kHz。

如果通信稳定，再慢慢提高到：

```text
500 kHz
1 MHz
5 MHz
```

## 9.5 用示波器/逻辑分析仪看四根线

加载 `bmi160_spi_board.ko` 的瞬间，驱动会读 chip id。此时看：

```text
PD05 CS
PD00 CLK
PD01 MOSI
PD02 MISO
```

判断：

```text
CS 不拉低：
    CS 配置错，PD05 不对，或者 controller_data 没生效

CLK 没波形：
    soc_spi 没起来，或者 PD00 复用不对

MOSI 没波形：
    MOSI 配置不对

MISO 一直低：
    BMI160 没响应、没供电、MISO 接错、CS 错、模式错

MISO 一直高：
    MISO 悬空/上拉/芯片没响应
```

当前你读到 `0x00`，重点看 **MISO 是否一直低**。

# 5. raw 数据怎么换算成真实单位？

IIO 通常用这个公式：

```text
物理值 = raw × scale
```

加速度：

```sh
cat in_accel_scale
```

然后：

```text
accel_x = in_accel_x_raw × in_accel_scale
```

单位通常是：

```text
m/s²
```

陀螺仪：

```sh
cat in_anglvel_scale
```

然后：

```text
gyro_x = in_anglvel_x_raw × in_anglvel_scale
```

单位通常是：

```text
rad/s
```

如果你想换成 `g`：

```text
g = m/s² / 9.80665
```

如果你想换成 `°/s`：

```text
deg/s = rad/s × 57.2958
```

# 6. 一个简单 shell 脚本：实时查看 IMU

可以在板子上创建：

```sh
vi /tmp/read_bmi160.sh
```

内容：

```sh
#!/bin/sh

IIO_DEV=""

for d in /sys/bus/iio/devices/iio:device*; do
    name=$(cat "$d/name" 2>/dev/null)
    if [ "$name" = "bmi160" ]; then
        IIO_DEV="$d"
        break
    fi
done

if [ -z "$IIO_DEV" ]; then
    echo "BMI160 IIO device not found"
    exit 1
fi

echo "BMI160 device: $IIO_DEV"

ACC_SCALE=$(cat "$IIO_DEV/in_accel_scale" 2>/dev/null)
GYRO_SCALE=$(cat "$IIO_DEV/in_anglvel_scale" 2>/dev/null)

echo "accel scale: $ACC_SCALE"
echo "gyro  scale: $GYRO_SCALE"

while true; do
    ax=$(cat "$IIO_DEV/in_accel_x_raw")
    ay=$(cat "$IIO_DEV/in_accel_y_raw")
    az=$(cat "$IIO_DEV/in_accel_z_raw")

    gx=$(cat "$IIO_DEV/in_anglvel_x_raw")
    gy=$(cat "$IIO_DEV/in_anglvel_y_raw")
    gz=$(cat "$IIO_DEV/in_anglvel_z_raw")

    echo "accel_raw: x=$ax y=$ay z=$az | gyro_raw: x=$gx y=$gy z=$gz"

    sleep 0.1
done
```

运行：

```sh
chmod +x /tmp/read_bmi160.sh
/tmp/read_bmi160.sh
```

# 9. 应用程序里怎么读？

最简单就是 C 程序读 sysfs 文件。

例如读加速度 X：

```c
#include <stdio.h>
#include <stdlib.h>

static int read_int_file(const char *path)
{
    FILE *fp = fopen(path, "r");
    int val = 0;

    if (!fp) {
        perror(path);
        return 0;
    }

    fscanf(fp, "%d", &val);
    fclose(fp);

    return val;
}

int main(void)
{
    const char *base = "/sys/bus/iio/devices/iio:device0";

    char path[256];

    snprintf(path, sizeof(path), "%s/in_accel_x_raw", base);
    int ax = read_int_file(path);

    snprintf(path, sizeof(path), "%s/in_accel_y_raw", base);
    int ay = read_int_file(path);

    snprintf(path, sizeof(path), "%s/in_accel_z_raw", base);
    int az = read_int_file(path);

    printf("accel raw: x=%d y=%d z=%d\n", ax, ay, az);

    return 0;
}
```

调试阶段用 sysfs 很方便。

```text
iio:device0
```

然后你才能这样读：

```sh
cd /sys/bus/iio/devices/iio:device0

cat name
cat in_accel_x_raw
cat in_accel_y_raw
cat in_accel_z_raw
cat in_anglvel_x_raw
cat in_anglvel_y_raw
cat in_anglvel_z_raw
```

现在 `/sys/bus/iio/devices/` 是空的，说明还没到这一步。

---

## 下一步要解决的是 chip id 读 0

你现在应该先用 `cmd_spi` 或示波器确认 SPI 通信。

先卸载 BMI160，释放 `spi0.0`：

```sh
cd /tmp/kernel_drv_mode

rmmod bmi160_spi_board 2>/dev/null
rmmod bmi160_spi 2>/dev/null
rmmod bmi160_core 2>/dev/null
```

然后加载 spidev：

```sh
insmod spidev_helper.ko 2>/dev/null
insmod spidev.ko 2>/dev/null
```

添加一个 spidev 设备，CS 用你的 PD05：

```sh
cmd_spi add_dev 0 pd05
```

看有没有：

```sh
ls /dev/spidev*
ls /sys/bus/spi/devices/
```

然后先用 MODE 0、100kHz 读 BMI160 芯片 ID：

```sh
cmd_spi set /dev/spidev0.0 mode=0x00 speed=100000 bits=8 lsb=0
cmd_spi info /dev/spidev0.0
cmd_spi transfer /dev/spidev0.0 0x80 0x00
```

BMI160 的 ID 寄存器是 `0x00`，SPI 读命令一般是 `0x80`，所以返回的第二个字节应该是：

```text
d1
```

也就是理想情况：

```text
receive[1]: d1
```

如果返回还是：

```text
receive[1]: 00
```

说明底层 SPI 没和 BMI160 通上。

---

## 再试 MODE 3

```sh
cmd_spi set /dev/spidev0.0 mode=0x03 speed=100000 bits=8 lsb=0
cmd_spi transfer /dev/spidev0.0 0x80 0x00
```

如果 MODE 3 能读到 `d1`，那就把你的 `bmi160_spi_board.c` 改成：

```c
.mode = SPI_MODE_3,
```

然后重新编译 `bmi160_spi_board.ko`。

---

## 如果 MODE 0 / MODE 3 都读到 00

重点查硬件：

```text
PD00 -> BMI160 SCK
PD01 -> BMI160 MOSI / SDI
PD02 -> BMI160 MISO / SDO
PD05 -> BMI160 CSB
VDD / VDDIO 供电正常
GND 共地
```

特别容易错的是：

```text
MOSI/MISO 接反
CS 不是 PD05
BMI160 没供电
CS 没拉低
MISO 一直低
SPI mode 不对
```

你现在读到 `0x00`，很像 **MISO 没有有效返回**。

---

## 当前结论

你现在不是读法错，而是：

```text
IIO 设备还没生成
因为 BMI160 probe 失败
probe 失败原因是 chip id 读到 0x00
```

先把这个读 ID 问题解决：

```text
cmd_spi transfer /dev/spidev0.0 0x80 0x00
```

能返回 `d1` 之后，再重新加载 BMI160 驱动，`/sys/bus/iio/devices/iio:device0` 才会出现。
