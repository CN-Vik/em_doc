对，`menuconfig` 里从 `=m` 改成 `=y`，意思是：

```text
=m ：编译成 .ko 模块，需要 insmod/modprobe 加载
=y ：直接编译进内核镜像，启动时随内核一起初始化
=n ：不编译
```

所以 **`=y` 不是自动加载 ko**，而是 **根本不生成这个驱动的 `.ko`，源码对应的 `.o` 会被链接进内核本体**。

---

## 举个 BMI160 的例子

如果你配置成：

```text
CONFIG_BMI160=m
CONFIG_BMI160_SPI=m
```

编译后会生成类似：

```text
bmi160_core.ko
bmi160_spi.ko
```

上板后需要手动或脚本加载：

```sh
insmod bmi160_core.ko
insmod bmi160_spi.ko
```

---

如果你配置成：

```text
CONFIG_BMI160=y
CONFIG_BMI160_SPI=y
```

那它们会被编译进内核镜像里：

```text
vmlinux / xImage / uImage / zImage
```

这时候一般不会再有：

```text
bmi160_core.ko
bmi160_spi.ko
```

也不需要：

```sh
insmod bmi160_core.ko
insmod bmi160_spi.ko
```

启动时内核会自动执行这些驱动里的初始化函数。

---

## 但是有个大坑：驱动进内核 ≠ 设备一定能出来

比如你把：

```text
CONFIG_BMI160_SPI=y
```

改好了，但还需要满足：

```text
1. SPI 控制器驱动也已经起来
2. SPI0 master 已经注册
3. 系统知道 SPI0 上挂了一个 BMI160
4. modalias / compatible 能匹配 bmi160_spi 驱动
5. CS / mode / speed 配置正确
```

否则会变成：

```text
BMI160 驱动已经在内核里
但是没有 spi_device
所以 probe 根本不会执行
也就不会生成 IIO 节点
```

这就像你把“司机”放进系统了，但系统还不知道“车”在哪里。

---

## 对 SPI + IIO + BMI160，整条链都要考虑

如果你想彻底不用手动加载 ko，理论上要这样：

```text
CONFIG_SPI=y
CONFIG_REGMAP_SPI=y

CONFIG_IIO=y
CONFIG_IIO_BUFFER=y
CONFIG_IIO_TRIGGERED_BUFFER=y

CONFIG_BMI160=y
CONFIG_BMI160_SPI=y
```

同时 SPI 控制器也得是内建：

```text
君正 SPI controller = y
```

如果 SPI 控制器还是：

```text
soc_spi.ko
```

那即使 BMI160 是 `=y`，启动时也可能找不到 SPI master。

因为流程会变成：

```text
内核启动
    ↓
BMI160 驱动已经初始化
    ↓
但是 soc_spi.ko 还没 insmod
    ↓
SPI0 master 不存在
    ↓
BMI160 设备注册/匹配失败
```

---

## `=y` 后还能不能 lsmod 看到？

看不到。

`lsmod` 只能看到动态加载的 `.ko` 模块。

比如：

```text
CONFIG_BMI160_SPI=m
```

加载后：

```sh
lsmod
```

可能看到：

```text
bmi160_spi
bmi160_core
```

但是如果：

```text
CONFIG_BMI160_SPI=y
```

那它是内核的一部分，`lsmod` 看不到。

你要用：

```sh
dmesg | grep -i bmi
```

或者：

```sh
cat /sys/bus/spi/drivers/bmi160*/uevent
```

再或者看 IIO：

```sh
ls /sys/bus/iio/devices/
cat /sys/bus/iio/devices/iio:device*/name
```

---

## 对你现在最重要的一句话

```text
=m 是生成 ko，运行时加载。
=y 是源码直接编进内核，不再靠 ko。
```

但是：

```text
驱动 =y 只是说明驱动代码进内核了；
设备能不能工作，还要看 SPI master、CS、SPI 设备注册、IIO 依赖是否也都配置对。
```

君正文档里那种 SPI 设备注册方式，本质还是 Linux SPI 框架：通过 `spi_board_info` 描述设备，通过 `spi_register_driver()` 注册驱动，通过 `spi_write_then_read()` 传输数据。 所以你后面如果想全内建，就不是“加载 ko”，而是要把 **SPI 控制器 + BMI160 驱动 + BMI160 设备注册信息** 都放进内核启动链路里。


----------
---------
--------
内核模块加载方式主要分 **4 大类**。你可以按这个理解：

```text
1. 手动加载
2. 自动依赖加载
3. 开机脚本加载
4. 编进内核，不再是模块
```

---

# 1. `insmod` 手动加载 `.ko`

这是最直接的方式：

```sh
insmod bmi160_core.ko
insmod bmi160_spi.ko
insmod bmi160_spi_board.ko
```

特点：

```text
优点：简单直接，适合调试
缺点：不会自动处理依赖
```

比如你直接：

```sh
insmod bmi160_spi.ko
```

如果它依赖 `bmi160_core.ko`，但是你没提前加载，就可能报：

```text
Unknown symbol xxx
```

所以 `insmod` 需要你自己知道加载顺序。

---

# 2. `modprobe` 自动加载依赖

`modprobe` 比 `insmod` 高级一点：

```sh
modprobe bmi160_spi
```

它会根据模块依赖关系，自动加载依赖模块。

比如理论上它可以帮你自动加载：

```text
industrialio.ko
regmap-spi.ko
bmi160_core.ko
bmi160_spi.ko
```

但是前提是系统里有：

```text
/lib/modules/$(uname -r)/
modules.dep
modules.alias
```

并且执行过：

```sh
depmod
```

常见命令：

```sh
depmod -a
modprobe bmi160_spi
```

特点：

```text
优点：自动处理依赖
缺点：嵌入式小系统里不一定带 modprobe/depmod
```

很多 Buildroot/BusyBox 系统可能只有 `insmod/rmmod/lsmod`，没有完整 `modprobe`。

---

# 3. 开机脚本自动加载

这个本质上还是 `insmod` 或 `modprobe`，只是放到启动脚本里自动执行。

比如在嵌入式系统里常见：

```text
/etc/init.d/Sxx_xxx
/etc/init.d/rcS
/etc/inittab
```

你可以写一个脚本：

```sh
#!/bin/sh

insmod /lib/modules/utils.ko
insmod /lib/modules/soc_spi.ko

insmod /lib/modules/industrialio.ko
insmod /lib/modules/kfifo_buf.ko
insmod /lib/modules/industrialio-triggered-buffer.ko

insmod /lib/modules/bmi160_core.ko
insmod /lib/modules/bmi160_spi.ko
insmod /lib/modules/bmi160_spi_board.ko
```

然后开机自动执行。

特点：

```text
优点：不用每次手敲
缺点：顺序错了还是会失败
```

你君正 X2600 这种系统，大概率就是这种方式比较常见。

---

# 4. 通过配置文件自动加载

在比较标准的 Linux 发行版里，可以把模块名写到：

```text
/etc/modules
/etc/modules-load.d/*.conf
```

比如：

```sh
echo "bmi160_spi" > /etc/modules-load.d/bmi160.conf
```

系统启动时会自动加载。

但是这个方式依赖系统服务，比如：

```text
systemd-modules-load
```

很多嵌入式 BusyBox/Buildroot 系统不一定有。

所以在 X2600 这种板子上，不一定适用。

---

# 5. 设备热插拔自动加载

有些模块会根据设备信息自动加载。

比如 USB 设备插上后，内核产生事件：

```text
modalias
uevent
udev/mdev
```

然后系统根据 `modules.alias` 自动加载对应驱动。

比如：

```text
USB 网卡插入
    ↓
内核上报 modalias
    ↓
udev/mdev 匹配 modules.alias
    ↓
自动 modprobe 对应驱动
```

SPI 设备理论上也可以通过 `modalias` 匹配，比如：

```text
spi:bmi160
```

但前提是系统有完整的自动加载机制。

在嵌入式系统里，这个经常不完善，所以很多时候还是手动 `insmod` 或启动脚本加载。

---

# 6. 编进内核：`=y`

这个严格来说 **不是模块加载方式**。

比如：

```text
CONFIG_BMI160=y
CONFIG_BMI160_SPI=y
```

意思是：

```text
源码直接编译进内核镜像
启动时随内核初始化
不生成 bmi160_core.ko / bmi160_spi.ko
不需要 insmod
lsmod 也看不到
```

所以：

```text
=m：生成 .ko，运行时加载
=y：编进内核，启动时初始化
=n：不编译
```

---

# 对你 X2600 + BMI160 来说

如果你走模块方式，最常见就是：

```text
方式 A：手动 insmod 调试
方式 B：写启动脚本自动 insmod
方式 C：如果系统支持 modprobe，就用 modprobe 自动依赖
```

比如调试阶段：

```sh
insmod utils.ko
insmod soc_spi.ko

insmod industrialio.ko
insmod kfifo_buf.ko
insmod industrialio-triggered-buffer.ko

insmod bmi160_core.ko
insmod bmi160_spi.ko
insmod bmi160_spi_board.ko
```

稳定后可以放到启动脚本里。

如果你想不用 `.ko`，那就改成：

```text
CONFIG_SPI=y
CONFIG_IIO=y
CONFIG_BMI160=y
CONFIG_BMI160_SPI=y
```

但同时还得保证：

```text
SPI 控制器驱动也进内核
BMI160 设备注册也进内核
CS / mode / speed / bus_num 配置正确
```

---

一句话总结：

```text
insmod：手动加载，不处理依赖
modprobe：自动处理依赖
启动脚本：开机自动 insmod/modprobe
udev/mdev：根据设备事件自动加载
=y：不是加载模块，而是直接编进内核
```
