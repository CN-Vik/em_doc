### **二、MCU任务调度处理（基于RTOS）**

无人机系统是一个多任务实时系统，必须使用RTOS（如FreeRTOS）来调度任务。

*   **任务划分**：根据功能模块，可以将系统划分为多个独立的任务（Task），每个任务拥有不同的优先级。
    *   **高优先级任务**：**传感器数据采集任务**。如图7所示，它可能由一个硬件中断（如MPU6050的数据就绪中断）触发，或者由一个高优先级的定时任务循环执行。它的职责是快速、及时地读取传感器数据并存入结构体。
    *   **最高优先级任务**：**姿态解算与控制任务**。这是无人机的核心。它需要以极高的频率（几百Hz到1KHz）运行，读取传感器数据，进行滤波和姿态解算（如互补滤波、卡尔曼滤波），并执行PID控制算法，计算出电机所需的PWM输出量。
    *   **中优先级任务**：**无线通信任务**。负责通过2.4GHz模块与地面站通信，发送状态数据（姿态、温度）和接收控制指令。
    *   **低优先级任务**：**电源管理任务**。监控电池电量，执行低功耗策略（如空闲时降低采样率）。

*   **任务间通信**：
    *   不同任务之间需要通过**队列（Queue）**、**信号量（Semaphore）**、**互斥量（Mutex）** 来进行数据同步和共享。
    *   例如，传感器任务将数据放入一个队列，控制任务从队列中取出数据进行计算。使用互斥量来保证对`g_mpu6050`这个共享资源的访问不会冲突。

*   **调度策略**：RTOS内核会基于任务的优先级进行**抢占式调度**。高优先级的控制任务可以随时抢占低优先级的通信任务，从而保证控制的实时性。

### **二、MCU任务调度处理（基于RTOS）**

无人机系统是典型的多任务实时系统，必须使用RTOS（如FreeRTOS）来调度。

*   **任务划分 (Task Partitioning)**：
    *   **最高优先级任务**：**姿态解算与控制任务**。核心任务，需以极高频率（500Hz-1kHz）运行，读取传感器数据，进行滤波融合，执行PID算法，输出PWM。
    *   **高优先级任务**：**传感器数据采集任务**。由硬件中断（图7的GPIO中断）或定时器触发，快速读取传感器数据并存入结构体。
    *   **中优先级任务**：**无线通信任务**。负责与地面站通信，发送状态数据，接收遥控指令。
    *   **低优先级任务**：**状态监控与电源管理任务**。监控电池电压，执行低功耗策略。

*   **任务间通信 (IPC)**：
    *   **队列 (Queue)**：用于传输大量数据。例如，传感器任务将数据包放入队列，控制任务从队列取出。
    *   **信号量 (Semaphore)**：用于同步。例如，在图7的中断服务例程(ISR)中**释放一个二值信号量**，传感器采集任务**等待**该信号量，从而触发数据读取。**（注意：面试时可强调您知道在ISR中不宜做复杂操作，最佳实践是只发信号）**
    *   **互斥量 (Mutex)**：用于保护共享资源。例如，保护全局结构体`g_mpu6050`，防止多个任务同时读写导致数据错乱。

*   **调度策略**：RTOS采用**基于优先级的抢占式调度**。高优先级的控制任务可以随时抢占低优先级的任务，保证控制的实时性。

### **三、可能会被问到的面试问题与答案（Q&A）**

**1. Q: 请详细介绍你这个无人机项目的软件架构。你是怎么思考的？**
*   **A**: 我的架构遵循分层和模块化原则，共分为五层。硬件层是基础；处理器/外设驱动层提供标准协议；**设备驱动层是我的设计重点，我通过结构体和函数指针实现了硬件抽象**，将具体传感器与上层应用解耦；应用层负责核心算法；RTOS层调度所有任务。这样做的最大好处是**可移植性和可维护性极佳**，更换硬件只需修改设备驱动层，应用层代码无需变动。

**2. Q: 我看你用了一个`IMU_Dev`结构体（图5/6），为什么用函数指针？有什么好处？**
*   **A**: 使用函数指针是为了实现**“面向接口编程”**。将“获取数据”等操作抽象为接口，设备驱动层去实现这些接口。这样做的好处是：
    *   **解耦**：应用层不依赖具体传感器的实现，只依赖接口。
    *   **可扩展**：添加新传感器时，只需实现一套新的接口函数，而无需修改应用层代码。
    *   **可测试**：可以轻松创建模拟传感器（Mock）进行单元测试。

**3. Q: 在中断函数（ISR，图7）里直接进行数据读取吗？这符合最佳实践吗？**
*   **A**: 您提的非常对。在图7中是为了演示接口调用，但在实际项目中，**中断服务程序应尽可能短小**。更优的做法是：在中断里仅发送一个信号量（Semaphore），然后由一个高优先级的**任务**来等待这个信号量，并在任务中进行实际的数据读取和处理。这样可以避免长时间关中断，影响系统实时性。

**4. Q: 如果多个任务都要访问全局变量`g_mpu6050`，如何保证数据安全？**
*   **A**: 这是一个典型的共享资源竞争问题。我会使用RTOS提供的**互斥量（Mutex）** 来实现对`g_mpu6050`的互斥访问。任何任务在读写前必须先获取互斥锁，操作完成后立即释放。这样可以确保数据的一致性。

**5. Q: 姿态解算你是怎么做的？了解哪些算法？**
*   **A**: （根据实际情况选择回答）MPU6050提供加速度和角速度原始数据。常用算法有：
    *   **互补滤波**：计算量小，易于实现，在资源有限的MCU上效果不错，是入门首选。
    *   **卡尔曼滤波**：精度高，但计算复杂，对MCU性能要求高。
    *   **DMP**：MPU6050自带的数字运动处理器，可以直接输出解算后的四元数，能大大减轻MCU负担。我的代码中`mpu_dmp_get_data`函数（图6）就是调用了DMP功能。

**6. Q: 如何管理和优化功耗？（结合图1）**
*   **A**: 我从软硬件两方面考虑：
    *   **硬件**：选择低功耗元件，设计高效的电源电路（如使用低Dropout的LDO）。
    *   **软件**：
        *   利用RTOS的**空闲任务**和 **tickless 模式**，在无任务运行时让MCU进入睡眠模式。
        *   动态调整任务执行频率，例如悬停时降低传感器采样率和控制频率。
        *   关闭未使用的外设时钟。

**7. Q: 在开发中遇到了哪些挑战？如何解决的？**
*   **A**: （这是一个展示解决问题能力的绝佳机会）
    *   **挑战1**：IIC通信时序不稳定，容易受干扰。
    *   **解决**：使用逻辑分析仪抓取波形，精确调试延时，并增加了重传机制。
    *   **挑战2**：传感器数据噪声大，导致姿态不稳定。
    *   **解决**：在应用层实现了软件滤波算法（如一阶低通滤波），并对数据进行了校准。
    *   **挑战3**：多任务间资源共享冲突。
    *   **解决**：引入RTOS的互斥量机制，规范了资源访问流程。

## 1️⃣ 软件架构总体思路

无人机软件通常采用**分层、模块化、可扩展**的架构，方便升级和维护。典型分三层：

1. **驱动层（Driver Layer）**

   * 负责和硬件打交道。
   * 核心任务：

     * 读取传感器数据（IMU、GPS、气压计、视觉模块等）
     * 控制执行器（电机、舵机等）
     * 通信接口（I2C、SPI、UART、CAN等）
   * 特点：

     * 尽量做纯粹的硬件操作，不包含业务逻辑
     * 提供统一接口供上层调用

2. **中间层 / 硬件抽象层（Middleware / HAL）**

   * 把硬件数据包装成“对象/结构体”，统一接口。
   * 例子：

     ```c
     typedef struct {
         float acc[3];
         float gyro[3];
         float temperature;
     } IMU_Data;

     typedef struct {
         void (*set_speed)(float speed);
         void (*stop)();
     } Motor_Dev;
     ```
   * 功能：

     * 数据融合（如 IMU+GPS）
     * PID 控制算法封装
     * 定时任务管理、任务调度接口
   * 作用：

     * 上层不用关心硬件细节，直接操作结构体和接口

3. **应用层（Application Layer）**

   * 业务逻辑和飞控算法层
   * 功能：

     * 飞行模式管理（手动、姿态保持、定点悬停、自动巡航）
     * 飞行控制算法（PID/四元数/航迹规划）
     * 高级功能（避障、视频传输、数据记录）
   * 与中间层交互：

     * 读取传感器数据
     * 下发电机命令
     * 响应遥控器/地面站指令

## 3️⃣ 数据流设计

无人机的数据流通常如下：

```
传感器硬件 --> 驱动层 --> 中间层（滤波/融合/控制） --> 应用层（决策/飞行模式） --> 控制输出 --> 电机/舵机
```

注意：

* **传感器数据先经过滤波/融合**，保证稳定可靠。
* **控制算法层和应用层分离**，上层只下发目标姿态或速度，不直接操作硬件。

## 4️⃣ 软件架构设计注意点

1. **实时性**

   * 飞控对传感器数据和电机控制要求高，通常用 **RTOS** 或裸机循环+定时中断。
   * IMU 数据一般 200\~1000Hz，电机 PWM 控制 \~400Hz。

2. **模块独立**

   * 各模块接口清晰，便于替换或升级。
   * 例：换 IMU，只要 HAL 层改驱动，上层不变。

3. **任务调度**

   * 核心控制循环（飞控算法）
   * 外围任务（遥控解析、日志记录、通信）可放低优先级线程

4. **安全设计**

   * 断电保护、失控保护（Failsafe）
   * 遥控信号丢失自动降落
   * 电机过流/过温保护

---

## 5️⃣ 实际开发建议

1. 先把**驱动层和中间层**搭建好，确保数据采集和控制输出稳定。
2. 使用 **模块化接口**，上层只调用 `getSensorData()` 和 `setMotorSpeed()`。
3. 再做飞控算法和业务逻辑，逐步增加功能。
4. 建议用 **状态机管理飞行模式**，减少逻辑混乱。

## 3️⃣ 控制闭环

无人机核心是控制闭环：

```
         +-------------------+
         |   飞行控制器      |
         |  PID/LQR 计算输出 |
         +---------+---------+
                   |
                   v
             [电机驱动 PWM]
                   |
                   v
              [电机旋转]
                   |
                   v
            [IMU/GPS传感器]
                   |
                   +--> [数据融合/滤波] --> 回到飞行控制器
```

* **控制信号流**：上层任务/目标姿态 → 控制算法 → 电机输出
* **反馈信号流**：IMU/GPS/气压计 → 中间层滤波 → 飞行控制器修正输出
* 遥控器指令和地面站指令也会参与闭环计算（例如改变目标姿态或速度）

## 4️⃣ 任务调度框架（例子，RTOS或裸机循环）

| 任务类型         | 执行频率       | 优先级 |
| ------------ | ---------- | --- |
| 飞控主循环        | 200\~500Hz | 高   |
| IMU/GPS传感器采集 | 200\~500Hz | 高   |
| 遥控解析/指令接收    | 50\~100Hz  | 中   |
| 数据记录/日志      | 10\~50Hz   | 低   |
| 图像处理/避障算法    | 20\~50Hz   | 中   |
| 地面站通信/遥测     | 10\~50Hz   | 低   |

* 核心思想：**高频任务保证飞行稳定，低频任务保证功能扩展**。
* 任务间通过 **消息队列、共享缓冲区、互斥锁** 或 **环形缓冲** 进行数据交换。
* 状态机控制任务执行条件，比如在“悬停状态”才执行航点规划任务。

}
