到新公司接手**智能猫砂盆项目代码**，千万别一上来就从 `main.c` 开始逐行看完整项目，这样很容易迷路。正确方法是：

**先跑起来 → 看业务流程 → 找入口 → 画模块关系 → 顺着一次完整动作追代码。**

---

# 一、第一目标：先搞清楚“这个产品在干什么”

智能猫砂盆本质上是一个**嵌入式状态机产品**，不是单纯的驱动项目。

你先把业务功能列出来：

| 功能模块       | 说明               |
| ---------- | ---------------- |
| 滚筒电机控制     | 清理、复位、抚平、倒砂、停止   |
| 猫检测        | 重量传感器、红外、雷达、霍尔等  |
| 安全保护       | 防夹、防堵转、防倾倒、超时保护  |
| 按键控制       | 手动清理、配网、模式切换     |
| WiFi/APP通信 | APP下发清理、模式、定时、参数 |
| 状态灯/蜂鸣器    | 显示工作状态、故障提示      |
| Flash参数保存  | 模式、清理延时、校准数据     |
| OTA升级      | WiFi升级固件         |
| 故障管理       | 电机异常、传感器异常、桶未装好等 |

先不要纠结代码细节，先搞懂：

> APP点“一键清理”后，设备到底经历了哪些状态？

比如：

```text
APP一键清理
    ↓
收到WiFi串口/网络指令
    ↓
解析成内部按键/命令事件
    ↓
进入清理业务状态机
    ↓
电机转到抚平位置
    ↓
电机转到复位位置
    ↓
电机转到清理位置
    ↓
停止3秒
    ↓
回到抚平/复位
    ↓
上报完成状态给APP
```

你把这个流程追通，项目就熟了一半。

# 二、第一天：先把项目跑起来

刚到公司第一天，优先做这些：

## 1. 编译通过

先问清楚：

```text
用什么IDE？Keil？IAR？VSCode？GCC？
用哪个SDK？
哪个分支是量产分支？
哪个工程是当前产品？
编译脚本怎么用？
烧录工具是什么？
```

你要先拿到一个稳定结果：

```text
代码能编译
固件能烧录
设备能启动
串口有日志
基本功能能跑
```

不要一开始就改代码。

---

## 2. 找到启动入口

一般 MCU 项目入口是：

```c
int main(void)
{
    system_init();
    bsp_init();
    app_init();

    while (1)
    {
        app_loop();
    }
}
```

或者 RTOS 项目是：

```c
int main(void)
{
    board_init();
    driver_init();
    app_task_create();
    vTaskStartScheduler();
}
```

你要重点找这些文件：

```text
main.c
app_main.c
system_init.c
board.c
bsp.c
task.c
app.c
mode.c
motor.c
uart.c
wifi.c
key.c
```

然后画一个简单启动流程：

```text
main()
 ├── 时钟初始化
 ├── GPIO初始化
 ├── UART初始化
 ├── 电机驱动初始化
 ├── 传感器初始化
 ├── WiFi模块初始化
 ├── 参数读取
 └── 进入主循环/创建任务
```

# 三、第二步：不要看全部代码，先看“主循环/任务”

你之前给过类似这种代码：

```c
void act_routine(void)
{
    u32 key_value = KEY_NULL;

    physic_key_value_get(&key_value);
    wifi_key_value_get(&key_value);

    switch_read_key(mode.mode_runing, key_value);

    clear_all_keytype_flag();
}
```

这类函数就非常关键。

因为它说明项目是这样设计的：

```text
物理按键
    ↓
WiFi按键/APP指令
    ↓
统一转换成 key_value
    ↓
交给 switch_read_key() 处理
    ↓
进入不同模式/状态机
```

也就是说，APP指令和物理按键可能被抽象成了同一种“按键事件”。

这是小家电/智能硬件里很常见的写法。

你要优先找这些核心函数：

```text
xxx_routine()
xxx_task()
xxx_loop()
switch_read_key()
mode_xxx()
motor_xxx()
uart_cmd_xxx()
wifi_cmd_xxx()
```

尤其注意名字里有这些单词的函数：

```text
routine
task
loop
proc
process
handler
dispatch
state
mode
run
work
```

这些一般都是业务调度入口。

# 四、第三步：顺着“一键清理”追代码

智能猫砂盆最核心的功能一般是**清理流程**。

你就拿它当切入点。

## 1. 从 APP 指令开始追

假设 APP 发了“一键清理”，你先找：

```text
clean
clear
cleaning
wash
roll
motor
wifi_cmd
uart_cmd
key_clean
```

如果代码里是中文拼音，也要搜：

```text
qingli
clean
clear
cln
```

可能会看到类似：

```c
#define KEY_CLEAN       0x01
#define CMD_CLEAN       0x10
#define MODE_CLEAN      1
```

或者：

```c
case WIFI_CMD_CLEAN:
    wifi_uart_cmd_state[i].state = KEY_SHORT;
    wifi_uart_cmd_state[i].key_val = KEY_CLEAN;
    break;
```

这说明：

```text
APP清理命令 → 转成内部 KEY_CLEAN
```

---

## 2. 再追按键处理函数

比如：

```c
switch_read_key(mode.mode_runing, key_value);
```

进去后可能是：

```c
switch (mode)
{
    case MODE_STANDBY:
        standby_key_process(key_value);
        break;

    case MODE_AUTO:
        auto_key_process(key_value);
        break;

    case MODE_CLEAN:
        clean_key_process(key_value);
        break;
}
```

继续追：

```c
case KEY_CLEAN:
    mode_set(MODE_CLEAN);
    break;
```

这时候你就知道：

```text
KEY_CLEAN 触发进入 MODE_CLEAN
```

---

## 3. 再追清理状态机

一般会有类似代码：

```c
void clean_mode_run(void)
{
    switch (clean_step)
    {
        case CLEAN_STEP_RESET:
            motor_run_to_reset();
            break;

        case CLEAN_STEP_FLAT:
            motor_run_to_flat();
            break;

        case CLEAN_STEP_CLEAN:
            motor_run_to_clean();
            break;

        case CLEAN_STEP_WAIT:
            motor_stop();
            break;

        case CLEAN_STEP_FINISH:
            mode_set(MODE_STANDBY);
            break;
    }
}
```

你要把它画成图：

```text
CLEAN_IDLE
   ↓
RESET_POS
   ↓
FLAT_POS
   ↓
RESET_POS
   ↓
CLEAN_POS
   ↓
STOP_3S
   ↓
FLAT_POS
   ↓
FINISH
```

这个图比你看 1000 行代码都有效。

# 五、重点看这 6 类文件

到新公司看项目代码，建议按这个顺序看：

---

## 1. 配置文件

先看宏定义和产品配置。

常见文件：

```text
config.h
user_config.h
product_config.h
board_config.h
app_config.h
```

重点看：

```c
#define MOTOR_TYPE_DC
#define HAS_WIFI
#define HAS_WEIGHT_SENSOR
#define CLEAN_DELAY_TIME
#define AUTO_CLEAN_ENABLE
#define ROLL_MOTOR_PWM_MAX
```

这些决定了产品功能开关。

---

## 2. 硬件板级文件

常见文件：

```text
board.c
bsp_gpio.c
bsp_uart.c
bsp_pwm.c
bsp_adc.c
bsp_timer.c
```

你要整理：

| 硬件        | MCU引脚    | 用途        |
| --------- | -------- | --------- |
| 滚筒电机PWM   | PAx      | 控制电机速度    |
| 电机方向      | PBx      | 正转/反转     |
| 霍尔/限位     | PCx      | 检测位置      |
| 重量ADC     | ADCx     | 猫进入检测     |
| WiFi UART | USARTx   | 和WiFi模块通信 |
| 按键        | GPIO     | 手动控制      |
| LED       | GPIO/PWM | 状态显示      |

这一步很重要，因为你要知道：

> 代码里的 motor、sensor、wifi 到底对应板子上的哪个硬件。

---

## 3. 驱动层文件

例如：

```text
motor_driver.c
weight_sensor.c
ir_sensor.c
hall_sensor.c
wifi_uart.c
flash.c
key.c
led.c
buzzer.c
```

这一层主要关心：

```text
怎么初始化？
怎么读？
怎么写？
有没有中断？
有没有DMA？
有没有定时器？
```

比如电机驱动你要看：

```c
motor_init();
motor_forward();
motor_reverse();
motor_stop();
motor_set_pwm();
motor_get_position();
motor_is_blocked();
```

---

## 4. 服务层/中间层文件

这一层最关键，通常是把底层驱动封装成产品功能。

例如：

```text
motor_service.c
clean_service.c
cat_detect_service.c
fault_service.c
wifi_service.c
param_service.c
```

比如底层是：

```c
motor_forward();
motor_reverse();
motor_stop();
```

服务层可能封装成：

```c
cat_litter_go_reset_pos();
cat_litter_go_clean_pos();
cat_litter_go_flat_pos();
cat_litter_check_motor_timeout();
```

这一层你要重点看，因为它最接近业务。

---

## 5. APP业务层文件

例如：

```text
app_clean.c
app_auto.c
app_mode.c
app_key.c
app_fault.c
app_main.c
```

这里决定：

```text
什么时候清理
什么时候禁止清理
什么时候报警
什么时候上报APP
什么时候进入待机
```

比如：

```c
if (cat_left && auto_clean_enable)
{
    start_clean_after_delay(5 * 60);
}
```

这才是产品逻辑。

---

## 6. 通信协议文件

智能猫砂盆一般有 WiFi/蓝牙模块，MCU 和通信模块之间可能走 UART。

你重点看：

```text
wifi_protocol.c
uart_protocol.c
cmd_parse.c
app_cmd.c
tuya.c
aliyun.c
mqtt.c
```

重点搞清楚：

```text
APP发来的命令格式是什么？
MCU怎么解析？
MCU怎么上报状态？
有没有心跳包？
有没有校验和？
有没有命令应答？
```

例如：

```text
APP命令：一键清理
WiFi模块收到
UART发给MCU
MCU解析 CMD_CLEAN
转换成 KEY_CLEAN
进入清理模式
清理完成后上报 CLEAN_DONE
```

# 七、快速熟悉代码的核心方法：抓 5 条主线

你不要平均用力看所有代码，而是抓主线。

## 主线 1：启动主线

```text
main()
 → system_init()
 → driver_init()
 → app_init()
 → while/task
```

搞清楚设备怎么启动。

---

## 主线 2：清理主线

```text
APP/按键触发清理
 → key/cmd
 → mode
 → clean state machine
 → motor action
 → finish/report
```

这是智能猫砂盆最核心业务。

---

## 主线 3：自动清理主线

```text
猫进入
 → 重量/传感器检测
 → 猫离开
 → 延时5分钟
 → 自动清理
```

这条线涉及产品体验。

---

## 主线 4：安全保护主线

```text
电机运行
 → 检测堵转/超时/限位/猫进入
 → 立即停止
 → 报警
 → 上报APP
```

这条线涉及安全，必须重点看。

---

## 主线 5：通信主线

```text
APP命令
 → WiFi模块
 → UART协议
 → MCU解析
 → 执行动作
 → 状态上报
```

这条线决定 APP 和 MCU 如何协作。

# 八、你可以直接用这个“看代码模板”

每看一个模块，就回答这几个问题：

```text
1. 这个模块负责什么？
2. 它对外提供哪些API？
3. 它依赖哪些底层驱动？
4. 它被哪些上层模块调用？
5. 它有没有状态机？
6. 它有没有定时器？
7. 它有没有中断？
8. 它有没有全局变量？
9. 它有没有错误处理？
10. 它和APP/WiFi有没有关系？
```

比如看 `motor.c`：

```text
1. 负责滚筒电机控制
2. 提供 motor_forward/motor_reverse/motor_stop
3. 依赖 PWM/GPIO/ADC/霍尔
4. 被 clean_service 调用
5. 有电机运行状态
6. 有超时检测
7. 可能有霍尔中断
8. 有 motor_state 全局变量
9. 有堵转/过流/超时保护
10. 清理完成后可能通知WiFi上报
```

这样看代码才有结构。

# 十二、一个非常实用的技巧：从日志反推代码

如果项目有串口日志，比如：

```text
[clean] start
[motor] go reset
[motor] reach reset
[motor] go clean
[clean] finish
```

你可以直接全局搜索：

```text
clean start
go reset
reach reset
clean finish
```

这样能非常快定位到核心代码。

如果日志太少，你可以自己临时加日志：

```c
printf("[CLEAN] step = %d\r\n", clean_step);
printf("[MOTOR] state = %d, pwm = %d\r\n", motor_state, pwm);
printf("[KEY] key_value = 0x%08X\r\n", key_value);
printf("[WIFI] cmd = 0x%02X\r\n", cmd);
```

但是注意：
**电机控制、定时器中断、通信中断里面不要乱加大量 printf**，容易影响时序。

# 十三、总结一句话

你到新公司熟悉智能猫砂盆代码，不要从底层一点点硬啃，而是按这个顺序：

```text
先跑起来
再看启动流程
再看主循环/任务
再追一键清理流程
再追电机控制
再追传感器和安全保护
最后看通信协议和参数保存
```

核心思路是：

```text
用业务流程带着你看代码，而不是被代码牵着走。
```

对于智能猫砂盆，最值得你第一个追通的流程就是：

```text
APP/按键一键清理 → 命令解析 → 模式切换 → 清理状态机 → 电机动作 → 安全检测 → 完成上报
```

把这条线搞明白，你基本就能开始改 bug 和加功能了。


> 不要试图一次性看懂整个项目，而是先把“数据怎么流动、状态怎么变化、谁在改全局变量”搞清楚。

# 一、先别急着重构，先做“代码侦察”

新公司刚接手项目，千万不要一上来就说：

```text
这代码太烂了，我要重构。
```

这样风险很大。

你第一阶段目标不是改好它，而是：

```text
能编译
能烧录
能复现功能
能知道某个功能从哪里进、从哪里出
能知道关键全局变量是谁改的
```

也就是先做到：

```text
看不懂全部代码，但能追通一条业务链路。
```

比如智能猫砂盆，先追：

```text
APP一键清理 / 按键清理
    ↓
命令解析
    ↓
模式切换
    ↓
清理状态机
    ↓
电机动作
    ↓
传感器/限位/堵转判断
    ↓
完成/故障上报
```

只要这一条线能看懂，项目就打开口子了。

# 二、看不明白的地方，先问自己 5 个问题

遇到一个看不懂的函数，不要一行一行死磕。先问：

```text
1. 这个函数什么时候被调用？
2. 谁调用它？
3. 它修改了哪些全局变量？
4. 它依赖哪些全局变量？
5. 它最终影响了什么硬件动作？
```

比如看到：

```c
void clean_routine(void)
{
    if (clean_flag)
    {
        motor_run();
        clean_step++;
    }
}
```

不要只盯着 `clean_step++` 看，要查：

```text
clean_flag 是谁置 1 的？
clean_step 谁清零？
motor_run() 里面控制哪个 IO/PWM？
clean_routine() 多久调用一次？
clean_step 加到多少会结束？
```

你要追的是**调用关系和变量变化**，不是单纯看语法。

# 三、全局变量满天飞，最重要是找“写入点”

全局变量多不可怕，最怕不知道谁在改。

比如有个全局变量：

```c
u8 clean_step;
u8 motor_state;
u8 mode_runing;
u32 key_value;
u8 fault_flag;
```

你不要先管它定义在哪里，第一步是全局搜索：

```text
clean_step =
clean_step++
clean_step--
clean_step +=
```

也就是只找**写入位置**。

因为读它的地方可能很多，但真正改变系统状态的是写它的地方。

---

## 对每个关键全局变量，做一张表

比如：

| 全局变量               | 作用     | 谁写它                            | 谁读它          | 风险           |
| ------------------ | ------ | ------------------------------ | ------------ | ------------ |
| `mode.mode_runing` | 当前运行模式 | `mode_set()`、按键处理、故障处理         | 主循环、状态机      | 多处改模式，容易乱跳   |
| `clean_step`       | 清理流程步骤 | `clean_mode_run()`、异常处理        | 电机控制、显示上报    | 没有统一复位，可能卡状态 |
| `motor_state`      | 电机状态   | `motor_start()`、`motor_stop()` | 堵转检测、APP上报   | 中断和主循环都可能改   |
| `fault_flag`       | 故障标志   | 传感器检测、电机保护                     | 模式控制、蜂鸣器、APP | 故障清除逻辑容易混乱   |

这个表非常有用。

你不用一下子做全项目，先做**核心变量表**：

```text
模式变量
电机状态变量
清理步骤变量
故障变量
按键/APP命令变量
传感器状态变量
```

---

# 四、全局变量分析方法：先分成 5 类

全局变量多的时候，你先把它们分类。

## 1. 状态类全局变量

比如：

```c
u8 mode_runing;
u8 clean_step;
u8 motor_state;
u8 wifi_state;
```

这种最关键，决定程序走向。

重点看：

```text
在哪里改变？
改变后会进入哪个流程？
有没有被异常处理强行修改？
```

---

## 2. 标志位类全局变量

比如：

```c
u8 clean_flag;
u8 cat_in_flag;
u8 fault_flag;
u8 key_press_flag;
```

这种通常是：

```text
某处置 1
某处处理
某处清 0
```

最容易出 bug 的地方是：

```text
置 1 后没人清
还没处理就被清了
多个地方同时改
中断里改，主循环里读
```

---

## 3. 计时类全局变量

比如：

```c
u16 clean_delay_cnt;
u16 motor_timeout_cnt;
u16 key_long_press_cnt;
```

重点看：

```text
多久加一次？
在哪里清零？
单位是 ms、10ms、25ms 还是 1s？
超时阈值是多少？
```

很多项目坑就在这里。

比如代码里写：

```c
if (motor_timeout_cnt > 200)
```

但你不知道这个 `200` 是：

```text
200ms？
2s？
5s？
```

这时候要看它在哪个周期函数里加。

如果是在 25ms 调用一次的函数里：

```text
200 * 25ms = 5000ms = 5秒
```

---

## 4. 数据缓存类全局变量

比如：

```c
u8 uart_rx_buf[128];
u8 wifi_cmd_buf[64];
u16 adc_value[8];
```

重点看：

```text
谁写入？
谁解析？
有没有长度保护？
有没有越界风险？
是否中断/DMA里写？
```

---

## 5. 配置参数类全局变量

比如：

```c
u8 clean_delay_time;
u8 auto_clean_enable;
u8 child_lock_enable;
u16 weight_threshold;
```

重点看：

```text
默认值在哪里？
Flash读取在哪里？
APP设置后是否保存？
恢复出厂设置是否会清掉？
```

---

# 五、别直接改全局变量，先“包一层”

如果项目里到处都是：

```c
mode.mode_runing = MODE_CLEAN;
```

```c
mode.mode_runing = MODE_IDLE;
```

```c
mode.mode_runing = MODE_FAULT;
```

这就很危险，因为谁都能改模式。

更好的做法是逐步改成：

```c
void app_mode_set(u8 new_mode)
{
    mode.mode_runing = new_mode;
}
```

然后以后新代码不要直接写：

```c
mode.mode_runing = xxx;
```

而是统一写：

```c
app_mode_set(MODE_CLEAN);
```

再进一步可以加日志：

```c
void app_mode_set(u8 new_mode)
{
    printf("[MODE] %d -> %d\r\n", mode.mode_runing, new_mode);

    mode.mode_runing = new_mode;
}
```

这样你马上能看到模式什么时候跳了。

这叫：

```text
先封装入口，不立刻大改结构。
```

# 六、看不懂状态机，就加日志画流程

智能猫砂盆这类产品最核心就是状态机。

比如清理流程可能是：

```c
switch (clean_step)
{
    case CLEAN_STEP_RESET:
        break;

    case CLEAN_STEP_FLAT:
        break;

    case CLEAN_STEP_CLEAN:
        break;

    case CLEAN_STEP_WAIT:
        break;

    case CLEAN_STEP_FINISH:
        break;
}
```

如果你看不懂它怎么跳，就加日志：

```c
static u8 last_clean_step = 0xff;

if (last_clean_step != clean_step)
{
    printf("[CLEAN] step change: %d -> %d\r\n", last_clean_step, clean_step);
    last_clean_step = clean_step;
}
```

这样设备跑一次清理，你串口会看到：

```text
[CLEAN] step change: 255 -> 0
[CLEAN] step change: 0 -> 1
[CLEAN] step change: 1 -> 2
[CLEAN] step change: 2 -> 3
[CLEAN] step change: 3 -> 4
```

然后你就能反推：

```text
0 是复位
1 是抚平
2 是清理
3 是等待
4 是结束
```

比你硬看代码快很多。

# 七、调试全局变量，用这几招

## 1. 搜索写入点

这是最基本的：

```text
变量名 =
变量名++
变量名--
memset(&变量名
```

---

## 2. 加变化日志

比如：

```c
void motor_state_set(u8 state)
{
    if (motor_state != state)
    {
        printf("[MOTOR] state: %d -> %d\r\n", motor_state, state);
        motor_state = state;
    }
}
```

---

## 3. 用调试器 Watch

如果有 J-Link / ST-Link，可以直接 watch：

```text
clean_step
mode_runing
motor_state
fault_flag
```

让程序跑起来，看变量什么时候变。

---

## 4. 用硬件断点/观察点

比如怀疑 `clean_step` 被莫名其妙改了。

你可以设置 watchpoint：

```text
当 clean_step 被写入时暂停
```

这样能直接抓到是哪行代码改的。

这个对“全局变量被乱改”特别有效。

---

# 八、不要从底层驱动开始看，先从“功能入口”开始

很多新人容易犯一个错：

```text
先看 GPIO
再看 UART
再看 PWM
再看 ADC
最后看业务
```

这样会很痛苦。

智能猫砂盆项目应该倒过来：

```text
先看业务入口
再看状态机
再看服务层
最后看底层驱动
```

比如你要看“清理功能”，顺序应该是：

```text
APP命令 / 按键
    ↓
clean_start()
    ↓
clean_step 状态机
    ↓
motor_action_xxx()
    ↓
motor_forward/motor_reverse/stop
    ↓
PWM/GPIO
```

你要看的是：

```text
业务怎么调用驱动
```

而不是一开始就研究 PWM 寄存器。

# 九、遇到特别乱的代码，采用“外围包围法”

老代码很乱，不能一下子推翻。

你可以这样做：

```text
旧代码保持不动
新需求写在新模块
旧代码只开放几个接口
慢慢把全局变量收口
```

比如你可以新建：

```text
app_clean_service.c
app_motor_service.c
app_fault_service.c
app_param_service.c
```

然后不要让新业务直接碰底层乱变量，而是包一层：

```c
void litter_clean_start(void)
{
    clean_flag = 1;
    clean_step = CLEAN_STEP_START;
}

void litter_clean_stop(void)
{
    clean_flag = 0;
    motor_stop();
}

u8 litter_clean_is_busy(void)
{
    return clean_flag;
}
```

虽然内部还是旧变量，但外部调用变干净了。

这叫：

```text
先统一入口，再慢慢治理内部。
```

# 十、不要追求一次性看懂，要做“局部可控”

你可以把项目分成三类区域：

## 1. 已理解区域

比如：

```text
按键扫描
APP命令解析
清理状态机入口
```

这些可以做笔记。

---

## 2. 半理解区域

比如：

```text
电机到位判断
堵转检测
重量传感器滤波
```

这些先标记，不要马上改。

---

## 3. 暂时黑盒区域

比如：

```text
WiFi模组底层协议
OTA升级
产测模式
历史兼容代码
```

这些先当黑盒，只知道输入输出。

你刚接手项目，不需要全部看懂。实际工作中很多老员工也不是全懂，只是知道关键链路。

# 十一、可以给自己建一个“项目地图”

建议你自己建一个文档：

```text
智能猫砂盆代码地图.md
```

内容这样写：

```text
1. 编译烧录方式
2. 串口日志波特率
3. main启动流程
4. 周期任务列表
5. 全局变量表
6. 模式状态机
7. 清理流程状态机
8. 电机控制接口
9. APP命令表
10. 故障码表
11. 当前不理解的问题
```

尤其是这个表很重要：

```text
函数名              作用                 调用周期/调用者
act_routine         处理按键和APP命令      25ms
clean_routine       清理流程状态机         25ms/100ms
motor_routine       电机运行检测           10ms/25ms
fault_routine       故障检测               100ms
wifi_routine        APP通信处理            主循环
```

有了这个表，混乱代码就开始变得有结构。

# 十二、问老员工也要讲技巧

不要问：

```text
这代码怎么看？
```

别人很难回答。

你要问具体问题：

```text
clean_step 是清理流程的主状态吗？
mode_runing 是不是全局模式？
APP一键清理最后是不是转成 KEY_CLEAN？
电机到位是靠霍尔还是电流判断？
motor_state 是不是只能在 motor.c 里面改？
fault_flag 哪些故障会置位？
```

这样别人一听就知道你真的在追代码，也更愿意讲。

# 十四、最现实的建议

面对这种乱项目，你不要想着：

```text
我要把整个架构搞优雅。
```

而是先做到：

```text
1. 不被全局变量绕晕
2. 能知道一个功能从哪里触发
3. 能知道关键状态在哪里改
4. 能定位 bug 是哪条业务链的问题
5. 新增功能时尽量不继续污染旧代码
```

工作里真正有价值的是：

```text
在混乱代码里建立秩序。
```

你可以先从这几个核心变量开始整理：

```text
mode_runing        当前模式
clean_step         清理步骤
motor_state        电机状态
fault_flag         故障标志
key_value          按键/APP命令值
cat_state          猫进入/离开状态
```

把这几个变量的**写入点、读取点、变化流程**搞清楚，智能猫砂盆项目你基本就能开始接活了。
